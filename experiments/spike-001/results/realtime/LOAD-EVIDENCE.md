## 실행 조건과 명령

작업 디렉터리 `experiments/spike-001/realtime`, Node `v24.19.0`에서 실행했다. 아래는 경로를 줄인 실제 인수이며 실행 파일 절대 경로는 각 summary의 `command`에 보존되어 있다. 생략한 시간·반복 인수에는 위의 기본값이 적용됐다.

```powershell
node load.mjs --scenario base --connections 100 --core-passed
node load.mjs --scenario concentrated --connections 100 --core-passed
```

Windows 10.0.26200/x64, i7-11800H, 논리 프로세서 16개, 메모리 약 15.71GiB에서 생성기·앱·실험 DB가 같은 호스트를 사용했다. 연결은 실제 SSE 100개이며 입찰 회원 20명·관전자 역할 80명으로 구성했다. 주 서버 18081의 자동 판정 작업자를 사용했고, 18082의 판정 작업자는 `manual=true`였다. 후자의 outbox 조회는 계속 실행될 수 있다. 두 활성 서버에 부하를 분산한 측정은 아니다. 두 실행의 `load.mjs` SHA-256은 `02d6989233755b26607715f1c9c27d87fce573c791000e178852dd1ae12707a3`이며 다른 실행 소스 해시도 summary에 있다.

기본은 전체 2요청/초를 네 레인에 순환 배분했다. 집중은 레인 1에 5초마다 같은 조회 가격으로 20요청을 발행하고, 나머지 세 레인에 합계 1요청/초를 배분했다. 평균 발행률은 5요청/초다. 네 레인은 독립적 가격·마감 상태를 가졌다.

지연 경계는 **intent 등록 시작 → 최종 승인/거절 응답 관측**이다. ACK 완료와 브라우저 DOM 반영은 포함하지 않는다. 별도 `receiptToDecisionMs`는 DB에 기록된 `decidedMs−receivedMs`이며 물리적 판정 커밋·클라이언트 응답까지의 시간이 아니다. 모든 측정 요청의 두 DB 시각이 존재했고 음수 차이는 0건이었다. 프로토콜 p95 1초 충족은 별도 참고 지표이고, load의 조건/정확성 PASS와 구분한다.

연결·일정 조건도 6회 모두 충족했다. 500ms마다 관측한 연결 수 최소 100, 15초마다 관측한 서버 연결 수 최소 100, 계획 요청 수 누락 0, 발행이 한 슬롯(500ms) 이상 늦어진 건수 0, 클라이언트의 예상 밖 스트림 오류·공개 필드 오류 0, 작업자 오류 0이다. 표본 사이의 모든 순간을 증명하는 연결 계측은 아니다. 마지막 일치 검증은 작업자를 정지하고 모든 클라이언트를 **REST snapshot으로 다시 동기화한 뒤** 수행했으므로 이 항목만으로 SSE의 무손실 전달이나 전파 지연을 증명하지 않는다.

서버 `streamErrors` 절대값은 기본 1회차에서 처음/끝 0/0이고, 기본 2·3회차와 집중 1~3회차는 처음/끝 **100/100**이다. 각 회차의 24개 서버 표본에서도 같은 값이었다. 이 카운터를 전체 실행 중 오류 0으로 바꾸어 보고하지 않는다. 이번 회차 클라이언트가 기록한 예상 밖 오류 0과 기존 서버 카운터가 증가하지 않았다는 관측을 구분한다.

## 자원 표본과 범위

측정구간마다 주/보조 JVM·PostgreSQL·컨테이너 관측은 각각 20개다. JVM CPU는 인접 표본의 프로세스 CPU 누적 시간 차이로 계산한 19개 구간이며 **100%가 논리 코어 하나**다. 표의 값은 반복별 p95 또는 표본 최댓값이며 지속 사용률·순간 최대치가 아니다.

`xact_commit`은 해당 DB의 **첫 표본부터 마지막 표본까지** 증가량이다. 입찰 외 읽기 전용 트랜잭션, 타이머·outbox·상태 조회, 폴링·관측 작업이 포함되므로 **입찰 TPS나 입찰 커밋 수로 해석하지 않는다**. 같은 표본 범위에서 rollback·deadlock 증가량은 0이었다. SQL 표본의 락 대기 수 최대는 0, 미판정 요청은 기본 1회차에서 최대 1건·24ms이고 나머지에서는 0, 발행 표시가 없는 outbox 행은 모두 0이었다. 집중 판정 대기 시간이 실제로 수백 ms인 요청도 있었으므로 미판정 표본 0을 대기 부재로 해석할 수 없다.

구간 시작은 첫 `serverConnectionSample.serverMs−elapsedMs`로 추정했고 준비 시간 60초 이후를 측정구간으로 사용했다. HTTP 경로 지연은 정확히 보정되지 않았다. 자원 수집은 약 15초 간격의 HTTP 두 번·SQL·docker stats 순차 실행이므로 관측 시각이 서로 다르고 생성기와 같은 호스트에 부하를 더했다. 연결 풀 대기, GC 정지, 모든 락 대기·큐의 순간 최댓값은 측정하지 않았다.

## 별도 탐색 — 200연결 실패, 400연결 미실행

위 100연결 6회의 통계와 분리해 기록한다. 200연결 집중 탐색 `2026-10-15T03-40-20-964Z-concentrated-200`은 **FAIL / 실행 종료 코드 1**이었다. 준비 10초 + 측정 60초 × 1회이며, 근거는 [원시 summary](2026-10-15T03-40-20-964Z-concentrated-200/summary.json), [요청 JSONL](2026-10-15T03-40-20-964Z-concentrated-200/requests.jsonl), [원시 audit](2026-10-15T03-40-20-964Z-concentrated-200/audit-1.json), [별도 오프라인 분석](exploration-analysis.json)에 있다.

```powershell
node load.mjs --scenario concentrated --connections 200 --warmup-seconds 10 --measure-seconds 60 --repetitions 1 --core-passed --core-and-base-passed
```

입찰자20명과 평균5요청/초는 유지하고 관람 역할만80→180명으로 늘렸다. 입찰 부하도 두 배로 늘린 시험이 아니다.

준비 포함 350요청이 발행됐고 측정 300건 중 완료 146건(승인 30·거절 116), 실패 154건(`SYSTEM_ERROR` 100·`TIMEOUT` 54)이었다. 완료된 146건만의 응답 p95는 **6,500.352ms**, 최대 6,969.687ms다. 실패·미판정 154건은 이 지연 분포에 없으므로 전체 요청의 지연 보장으로 해석할 수 없고, 완료 표본 자체도 1초 참고값을 넘었다. 한 슬롯 이상 발행 지연도 57건이었다. `SYSTEM_ERROR` 100건에 저장된 메시지는 `Invalid final request outcome`이며 원 HTTP 응답 본문은 이 요청 JSONL에 없으므로 이를 HTTP 500 발생 100건으로 치환하지 않는다.

기록된 직접 오류는 `HikariPool-1` 연결 대기 시간 초과 **3,018ms**, 당시 **total=16, active=16, idle=0, waiting=88**이다. `workerErrors=1`, 자동 작업자 `manual=true`가 관측됐고 네 레인 모두 `held=true`, 사유 `WORKER_CONTINUITY_LOST`가 저장됐다. 최종 audit에는 `PENDING` 54건이 남았다. 연결 수 최소 200과 강제 snapshot 재동기화 후 불일치 0은 입찰 처리 실패를 상쇄하지 않는다. 서버 `streamErrors`는 이 탐색에서는 0→1로 증가했고 클라이언트의 stream/snapshot 오류 배열에도 14건이 기록됐다.

정책 검증기 오류는 아래와 같다. 이 검증기는 정상 진행하는 **bid-only fixture 전용**이며 장애 보류·미판정 상태를 재생하는 판정기가 아니다. 따라서 보류 이후의 `PENDING`을 모두 잘못된 최종 승인/거절로 분류하지 않는다. 다만 미판정 잔존과 실행 조건 실패는 실제 관측 사실이며 성공 판정을 내릴 수 없다.

# SPIKE-001 — 시간·시계·장애 범위의 ADR 입력

작성일: 2026-10-15. **검토 자료이며 ADR 확정·제품 정책 변경·운영 채택 승인이 아니다.** 이 메모는 현재 소스와 저장된 실행 증거를 읽어 작성했다. 새 서비스 시험·DB 호출은 수행하지 않았다. 전체 결과와 실행별 바이너리 구분은 [주 보고서](SPIKE-001.md)를 따른다.

정책 기준은 [D-055~D-057, D-067~D-074](../decisions/DECISION-LOG.md)이다. 공식 접수 기록·순번, 입찰 접수 시각에 따른 후속 마감, 실제 준비·재개 전이부터 전체 시간 부여, 장애 선후 불명 시 보류는 승인된 정책이다. 이 시각과 확정을 구현하는 기술적 계약이 남아 있다.

## 1. 현재 구현과 근거가 말하는 범위

| 논점 | 코드와 관측 | 판단 경계 |
| --- | --- | --- |
| 공식 접수 | [Engine.submit, 149–175행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L149): 레인 gate 획득·기존 요청/의도 검사 뒤 DB 시각과 증가 순번을 저장하고 commit한다. | HTTP 도착·연결 풀·gate 대기는 공식 접수 전이다. 마감 전 도착해도 공식 접수가 마감 뒤면 늦은 요청이 될 수 있다. HTTP 도착 순서의 공정성을 입증한 결과가 아니다. |
| 기록과 commit | [mutation, 41–55행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L41): 기록 시각을 포함한 작업이 끝난 뒤 commit한다. 같은 gate를 사용하는 타이머는 미commit 접수를 추월하지 못한다. | 기록 시각과 내구성 확정 시각은 다르다. 롤백된 접수를 과거 시각으로 되살리지 않으며, commit 결과 불명은 원키 조회·재시도로 확인해야 한다. |
| 준비·재개 시간 | [RESUME, 217–228행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L217), [moveNext, 297–303행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L297): 트랜잭션 안에서 읽은 `now`로 새 경계를 기록한다. | commit까지 시간이 흐른다. gate는 동시 변경을 막지만 commit 뒤 전체 시간을 확보하지 않는다. 실제 간격 관측은 재개 시험이며 다음 상품 준비에도 같은 형태의 위험이 있다는 것은 소스상 추론이다. |
| 시계 역행 | [접수 171행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L171), [판정 189–192행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L189), [tick 256–265행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L256): 이전/최신 접수 시각보다 작은 값이면 이력 불명 보류한다. | 마지막 판정·타이머 관측 시각을 기준으로 모든 역행을 탐지하지 않는다. 접수 이력이 없거나 후퇴한 값이 여전히 최신 접수보다 큰 경우, 앞으로 뛰는 시계는 탐지 보장이 없다. |
| worker 오류 | [ExperimentRuntime, 37–51행](../../experiments/spike-001/src/main/java/spike/ExperimentRuntime.java#L37): 오류를 관측한 JVM은 이후 pump 진입을 차단하고, 500ms 주기의 작업이 영속 보류를 기록한다. | 500ms는 장애 감지/보류 완료 상한이 아니다. 이미 진입한 다른 worker의 drain/tick, 다른 JVM, HTTP 접수까지 원자적으로 차단하지 않는다. |
| DB/JVM 재시작 | [DB epoch guard, 41–72행](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L41), [명시적 시작 복구, 24–30행](../../experiments/spike-001/src/main/java/spike/ExperimentRuntime.java#L24). | DB epoch 변경은 다음 guarded mutation 전에 보류한다. 생존 peer의 JVM 사망 감지·서비스 가용성 판단·분할/failover 판단 기능은 아니다. |

`Engine.java` 검토 시 SHA-256은 `9570BB928FB7448D7F7A58B3451B36170E833F3D04FB0BA34BA170087684385B`이다. 행 번호는 이 소스 기준이며 후속 변경 시 다시 대조한다.

실제 근거는 다음과 같다.

- [정확성 480/480](../../experiments/spike-001/results/correctness/20261015T021332Z-1e76d614/summary.json): 합성 시각으로 마감 전 접수·commit 틈·경계 순서·장기 판정 지연과 콜백 지연을 구분했다. 실제 시간에서 모든 대기/시계 이상을 검증한 자료가 아니다.
- [수정 후 회귀 100/100](../../experiments/spike-001/results/regressions/20261015T022437Z-6bae40cf/summary.json): 판정/타이머 시각이 최신 접수보다 이른 지정 사례가 포함된다. 실제 OS/DB 시계를 변경한 시험은 아니다.
- [DB 재시작 및 시간 간격](../../experiments/spike-001/results/environment-failures/20261015T023022Z-5bd892c1/summary.json): 실제 DB KILL/start 10회에서 마감 전 중단·epoch 변경·앱 PID 유지·보류를 확인했다. 별도 재개 10회의 수치와 계측 경계는 [주 보고서 §6](SPIKE-001.md#기록-시각과-postgresql-커밋-기록-시각--미해결-계약)이 원본이다. `pg_xact_commit_timestamp` 기준 간격이며 물리 내구성 완료·락 해제·COMMIT 응답 뒤 가용 시간의 직접 계측은 아니다. 간격 관측 성공이며 전체 시간 보장 성공이 아니다.
- [JVM 종료 40/40](../../experiments/spike-001/results/crashes/20261015T021920Z-cfc74566/summary.json), [SSE 경계 종료 20/20](../../experiments/spike-001/results/stream-crashes/20261015T023341Z-65be92ac/summary.json): 두 앱의 자동 판정을 끄고 명시적 `-Recover`로 재기동했다. 생존 peer가 자동 진행 중인 장애 시험으로 확대하지 않는다. 실행 JAR은 서로 다르다.

## 2. 후속 ADR에서 비교할 선택

| 선택 후보 | 지금 검토할 수 있는 이유 | 확정 전에 필요한 계약/근거 |
| --- | --- | --- |
| 현재 영속 접수·레인 gate 유지 | 공식 접수 이후 순서와 상태 원자성의 지정 사례 근거가 있다. | 접수 전 대기와 접수 기록→commit의 측정 분리, 대기 과다·기록 확정 불명 처리. HTTP 도착을 공식 접수로 바꾸는 결정과 혼동하지 않는다. |
| 트랜잭션 내부 전이 기록 시각을 권위 경계로 삼는 후보 | 현재 상태·시각을 같은 변경에 저장하는 방식과 가깝다. | 실제 전이 확정 시각 정책과의 적합성을 먼저 판단해야 한다. commit 지연·전체 시간·장기 지연 보류 기준이 해결되기 전에는 채택하지 않는다. commit 직전 시각을 다시 읽는 것만으로 간격이 없어지지 않는다. |
| commit과 연결된 별도 활성화 경계 후보 | 기록 시각과 외부에서 사용 가능한 전이의 차이를 명시적으로 다룬다. | 활성화 전 접수 처리, 시각의 영속 보존, projection 지연, 활성화 전/후 crash, 재시작 복원까지 설계해야 한다. [현재 commit timestamp 조회](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L349)는 계측용이며 운영 시각 저장 계약을 구현한 것이 아니다. |
| DB 시각 + 영속 시간 연속성 검증 | 여러 JVM이 한 권위 시각과 원기록을 공유한다는 최소 구조를 유지할 수 있다. | 어떤 기준과 정밀도로 후퇴/전진을 탐지할지, 이상 시 보류 범위와 복구 증거를 정해야 한다. 프로세스 단조 시계는 경과시간 관측에 유용하지만 단독으로 재시작·다중 JVM의 권위 시각을 대체하지 못한다. |
| 장애 감지와 영속 진행 권한 경계를 결합 | 정상 DB 접근만으로 정상 접수 가능성과 장애 선후가 입증되지는 않는다. | JVM 하나의 사망이 실제로 정상 접수 불능인지, 범위를 모르는 장애인지 구분해야 한다. 필요할 때 DB epoch/lease와 오래된 worker의 쓰기를 차단하는 방식을 비교한다. 단일 JVM 사망마다 무조건 전체 중단하는 정책을 추가하지 않는다. |

지금은 영속 접수·gate·원판정·outbox를 **설계 후보로 유지**할 근거가 있다. 시간 계약이나 분산 장애 감지 방식, 허용 지연값까지 확정할 근거는 없다. 임의의 운영 성능·장애 감지 임계값을 이 메모에서 정하지 않는다.

## 3. 필수 후속 실험 — 제안, NOT_RUN

아래는 이 메모에서 새로 실행하지 않은 실험이다. 기존 성공 건수에 더하지 않으며, 구현/주입 전에 시나리오별 기대값과 승인된 정책의 연결을 확인한다.

| 우선순위 | 실험과 필요한 관측 | 판단할 내용 |
| --- | --- | --- |
| 1 | 실제 DB 시계에서 마감 전 HTTP 요청을 pool/gate 앞에 대기시켜 마감 뒤 공식 접수. 도착·gate 획득·기록·commit·판정을 각각 기록한다. | 접수 전 지연과 접수 후 지연을 구별하고, 기록된 원접수·순번이 재시도에서도 보존되는지 확인한다. |
| 1 | 준비 진입/준비·최초·후속 재개에서 commit 지연을 단계 시간보다 짧게/길게 주입하고, 경쟁 접수·타이머·commit 전후 crash를 결합한다. | 선택한 전이 확정 경계에서 전체 시간, 구간 하한, 불명 시 보류를 동시에 만족하는지 비교한다. 현재 500ms 관측만으로 승인하지 않는다. |
| 1 | 한 JVM/worker의 오류 직전에 다른 레인 작업을 이미 진입시키고, 생존 peer 자동 판정을 켠 채 마감 전후에 종료/부분 연결 장애를 주입한다. | 감지 전·영속 보류 전·이미 진행 중 작업의 확정 가능성을 드러낸다. 정상 접수 지속 사례와 불능/선후 불명 사례의 기대값을 분리한다. |
| 2 | 수신 이력 없음, 최신 접수보다 큰 값으로 후퇴, 재개 직후 후퇴, 개시/마감을 넘는 전진을 주입한다. | 현재 탐지 범위 밖의 결과를 확인하고 영속 시각 기준·보류 범위를 비교한다. 합성 시각과 격리된 실제 시계 조정 시험은 별도 결과로 남긴다. |
| 2 | 같은 장애의 반복 관측·복수 JVM 관측·새 장애 중첩과 옛 재개를 교차시키고, 이력 불명에서 확인 가능한 상태로 복구하는 절차를 검증한다. | incident 중복과 새 발생을 구별하고 옛 재개를 차단한다. [현재 hold/confirm](../../experiments/spike-001/src/main/java/spike/core/Engine.java#L313)는 반복 incident 식별과 이력 불명 해제 절차를 완성하지 않는다. |

후속 ADR에는 선택한 **공식 기록/전이 확정 경계, 시계 연속성의 전제, 장애 발생·감지·보류의 서로 다른 시각, 진행 중 작업의 확정 권한, 복구 증거와 미검증 범위**를 명시해야 한다. 불확실한 이력을 추정 승인·거절·낙찰·유찰로 바꾸는 방안을 선택지로 추가하지 않는다.

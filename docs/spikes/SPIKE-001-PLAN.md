### E1. 공식 접수 순서·최고가·마감 경쟁

**목표:** 같은 레인의 외부 요청과 자동 개시·마감이 승인된 하나의 판정 이력으로 설명되는지 검증한다.

공식 접수는 인증·기본 형식 확인 후 공통 접수 기록에 넣는 경계다. 클릭·HTTP 도착·공유 의도 등록·판정 차례 진입과 구분한다. 경계 전 대기를 소급하지 않으며, 판정 작업이 시작될 때 공식 접수를 새로 만드는 방식으로 정책을 바꾸지 않는다.

**최소 실험 후보:** PostgreSQL에 레인별 영속 접수 기록을 먼저 저장하고, 공통 순번을 따라 판정한다. 짧은 접수 트랜잭션의 시각·순번·기록 확정을 함께 보호하며 판정 작업과 분리한다. 판정 트랜잭션에서는 레인 현재 대상·중단과 경매 상태를 같은 경쟁 제어 규약으로 확인하고, 입찰 기록·최고가·최고입찰자·단계·마감·원판정을 함께 변경한다. 시작 후보는 행 단위 비관적 락이다. 업무 판정 전에 오래된 금액·마감으로 선거절하지 않는다.

공식 접수의 저장 시각과 커밋 사이에 틈이 있다면 마감이 그 미완료 기록을 추월할 수 없게 해야 한다. 접수와 마감 확인에 공유하는 레인별 짧은 배타 경계를 후보로 삼고, 기록 직후 커밋 전 일시정지를 넣어 실제로 보호되는지 확인한다. 단순히 “현재 보이는 큐가 비었다”는 종료 조건은 검증 없이 채택하지 않는다.

`FOR UPDATE`는 배타적 변경을 위한 도구이고, 공식 접수 순번대로 판정하게 하는 규약은 별도로 필요하다. `nextval()` 번호의 크기만으로 미커밋 선행 기록을 모두 보았다고 판단하지 않는다. PostgreSQL sequence는 롤백에도 번호가 소진된다. 이로부터 낮은 번호의 늦은 커밋을 높은 cursor가 누락할 가능성을 추론하며 반례 실험으로 확인한다. [행 락](https://www.postgresql.org/docs/current/explicit-locking.html), [sequence](https://www.postgresql.org/docs/current/functions-sequence.html)

**재현 계획:** DB를 공유하는 애플리케이션 1프로세스와 2프로세스를 비교하고, barrier로 요청을 동시에 출발시킨다. 공식 접수 이후 선행 요청의 판정을 지연시켜 후행 작업이 추월하려는 상황을 만든다. 경계 시각의 정확한 비교는 실험 전용 제어 시계로 재현하고, 별도로 실제 DB 시계·HTTP·트랜잭션 통합 실행의 접수 이력을 수집한다. 합성 시계 결과를 실제 시간 성능으로 보고하지 않는다.

| 사례 | 승인 규칙으로부터의 기대 결과 — **실제 결과 아님** |
| --- | --- |
| 신규 회원 20명이 같은 유효 다음 금액으로 동시 제출 | 다른 거절 사유가 없는 자료에서 첫 유효 공식 순번 1건 승인, 나머지 19건 거절. 제출 금액 자동 인상 없음 |
| 선행 무효 요청, 후행 유효 요청 | 선행은 거절하고 후행은 자기 순번의 조건으로 승인 가능 |

| 입찰→중단/취소 및 중단/취소→입찰 | 요청 종류 우선권 없이 순번 적용. 선행 유효 효과·원상품 대상 유지 |
| 개시/현재 마감 직전·정각·직후, 늦은 개시/마감 작업 | 개시 정각은 개시 우선, 현재 마감 정각은 정상 종료 우선. 선행 입찰·제어와 장애 보류는 먼저 반영 |
| 재개 접수 뒤이지만 실제 재개 전 접수된 입찰 | 새 입찰은 거절. 원최종 판정 조회·재전송은 재판정하지 않음 |
| 한 레인 판정 일시정지, 나머지 세 레인 진행 | 다른 레인의 상품·가격·마감·결과는 독립. 공유 CPU·DB 자원에 의한 지연은 별도 측정 |

시각 정밀도는 실험 설정으로 고정·기록하며 제품 정책 확정으로 해석하지 않는다. 트랜잭션 시작 시각과 현재 시각 함수의 의미는 다르므로 장시간 락 대기·시각 채취 후 지연·주입한 시계 역행·재기동을 비교한다. 실제 OS 시계를 변경하지 않는다. 불명확한 시간 기록으로 정상 종료를 강제하지 않는다. [PostgreSQL 시각 함수](https://www.postgresql.org/docs/current/functions-datetime.html)

**성공 기준:** 모든 합의 사례에서 정책과 다른 승인·거절·중복 효과·잘못된 결과 각각 0건. 승인 기록과 최고값·마감·최종 결과의 DB 검증 및 공식 순번 재생 검증이 일치한다. 시각/순번 기록과 커밋의 틈에서도 선행 접수 누락 0건. 레인 간 상태 혼입 0건.

**남길 증거:** 공식 시각·순번, 요청의 원대상·원금액, 판정 전후 상태/버전, 승인·거절 사유, 현재 마감, 타이머의 원대상·예상 버전, 트랜잭션 실패, 접수/판정 대기와 락 대기. 실패 자료와 재현 seed를 함께 보존한다.

### E2. 중복·공유 의도·부분 실패·재시작

**목표:** 회원+요청번호의 원경매·금액·접수·최종 판정과 회원×경매의 미확인 제한을 함께 보존한다. 운영자+명령번호와 중단 발생 건도 같은 원결과 보존 원칙으로 검증한다.

**최소 실험 후보:** DB 고유성 제약과 트랜잭션으로 요청 키·내용 결합 및 회원×경매의 현재 공유 의도를 보호한다. 실제 입찰 전에 공유 의도 등록을 확인한다. 최종 승인/거절은 상태 효과와 같은 트랜잭션에 기록한다. 앱 확인은 원요청을 지정하고 현재 의도와 대조한다. 확인과 원기록 보존을 분리하여 늦은 중복이 새 요청이 되지 않게 한다. MVP 원판정 자동 TTL은 도입하지 않는다.

**재현 계획:** 다음 지점에서 요청/응답 차단, 저장 실패, 애플리케이션 강제 종료를 각각 주입하고 같은 DB로 다시 기동한다. DB 재시작도 별도로 수행한다. 전용 실험 데이터만 대상으로 하며 사용자의 다른 프로세스·DB를 종료하지 않는다.

| --- | --- |

| 등록 응답 유실 / 등록 미도달 | 조회·동일 등록 재시도로 확인. 등록 확인 전 실제 입찰 금지. 등록 시각은 공식 입찰 접수 아님 |
| 같은 요청을 두 프로세스에 동시 재전송 | 공식 원접수·원순번·원판정 유지, 논리 효과 한 번 |
| 같은 키로 금액 또는 경매를 변경 | 내용 충돌, 원기록 보존. 원요청 제한을 충돌로 해제하지 않음 |
| 공식 접수 기록 직전/직후, 판정 커밋 직전/직후 종료 | 커밋된 기록으로 원판정 또는 미결 복원. 미커밋 작업이 부분 효과를 남기지 않음. 커밋 불명은 조회·복구 증거로 해소 |
| 승인/거절 응답 유실, 종료 뒤 원요청 재전송 | 원최종 승인과 원최종 거절 모두 재사용. 최고가·마감 재변경 없음 |
| 첫 전송 미도달, 재전송이 첫 공식 접수 | 재전송의 공식 시각·순번 사용. 옛 클릭/등록 시각으로 소급 금지 |
| 앱 반영 확인 유실, 확인 재전송, 옛 확인과 새 의도 경쟁 | 어느 한 기기의 원최종 판정 반영 확인으로 해당 제한만 해제. 옛 확인이 새 미확인 의도를 해제하지 않음 |
| 성공한 재개 재전송, 새 중단 뒤 옛 재개, 옛 미접수 재개의 지연 도착 | 원결과·원실제 재개 시각 보존, 새 중단 유지. 새 재개 키도 진행 중 시간을 재부여하지 않음 |
| 재기동, 수동 중단+장애 보류, 장애·마감 선후 불명 | 확정 결과 유지, 증거에 맞는 보류 범위 유지. 운영자 확인·명시적 재개 전 자동 진행 금지 |
| 개인 응답 유실·단순 조회 기록 없음과 권위 이력 불명 복구의 비교 | 앞 상황만으로 레인 전체 보류하지 않음. 뒤 상황은 보류, 자동 거절·유찰·취소로 대체 금지 |

완전한 공식 이력의 미결 요청은 원시각·순번으로 판정한다. 장애가 먼저이거나 마감과의 선후를 알 수 없으면 결과 보류, 단일 레인 영향이 확실하면 해당 레인만, 전체 장애/범위 불명이면 현재 회차 미완료 레인 모두 보류한다. 저장된 최고입찰·단계·미결 기록을 확인하고 정상 접수/기록 가능성을 확인해야 재개할 수 있다.

**성공 기준:** 같은 키의 논리 효과 최대 한 번, 원판정 변경 0건, 부분 상태 커밋 0건, 앱 확인 전 잘못된 제한 해제 0건, 새 중단의 잘못된 해제 0건. 기록이 완전한 경우 복원 결과가 종료 전 기록과 일치하고, 불명인 경우 보류를 유지한다. 회원·경매가 다른 요청은 이 제한으로 함께 차단되지 않는다.

**남길 증거:** 장애 주입 지점, 실제 종료/재기동 명령과 종료 코드, DB 최종 조회, 원접수·원판정, 공유 의도/확인 변화, 중단 발생 건과 사유, 복구 가능·불명 판별 근거. 프로세스 강제 종료 시험을 디스크 손실·DB 고가용성 검증으로 보고하지 않는다.

### E3. 저장·이벤트 전달·재연결 상태 수렴

**목표:** 커밋된 상태가 전파 실패로 사라지지 않으며, 이벤트 유실·중복·역전과 상품 교체 중 재연결에도 현재 상태와 원요청 판정을 올바르게 복원한다.

**최소 실험 후보:** 상태·원판정·레인별 상태 버전·전송할 이벤트 기록(outbox)을 한 DB 트랜잭션으로 저장한다. 커밋 이후 dispatcher가 SSE로 통지하고 실패 시 재시도한다. 한 페이지에 하나의 스트림을 열어 네 레인의 변경을 구분하며 요청·조회·확인은 REST로 처리한다. 실험용 화면은 각 레인의 현재 상품·최고가·마감·진행/중단/보류/결과와 본인 원요청 판정을 표시한다.

Spring의 커밋 이후 이벤트 훅은 트랜잭션 단계에 맞춘 호출 기능이다. 그 훅만으로 프로세스 종료 이후 전파 복원을 보장할 수 없다는 설계 추론을 검증한다. outbox도 전송 성공 직후 발행 기록 전 종료하면 중복될 수 있으므로 중복 허용과 버전 검사가 필요하다는 가설을 시험한다. [Spring 트랜잭션 이벤트](https://docs.spring.io/spring-framework/reference/data-access/transaction/event.html)

**재현 계획:** 커밋 후 전송 전 종료, 전송 후 발행 처리 전 종료, 이벤트 일부 유실·중복·순서 역전, 오래된 이전 상품 이벤트, 클라이언트 단절 중 입찰·마감·상품 교체, snapshot 조회 중 신규 변경, 느린 관람자, 전체 dispatcher 중단과 특정 연결 단절을 각각 주입한다. 재생 cursor보다 낮은 번호의 늦은 커밋도 누락 반례로 시험한다.

snapshot과 이벤트 구독 사이의 변경을 놓치지 않도록, 실험 후보는 구독 연결과 버퍼 준비 뒤 권위 snapshot+레인별 버전을 읽고 snapshot 버전 이후 이벤트를 적용하는 순서다. 재생이 가능하면 동일 기준으로 병합하고, cursor 공백·버퍼 초과·재생 불가 시 snapshot을 다시 받는다. 이벤트가 아무것도 오지 않아 마지막 유실을 발견하지 못하는 경우를 위해 heartbeat에 권위 버전 확인 또는 주기적 재조회 후보를 포함한다. 구체 주기·버퍼 상한은 실험 설정으로 기록한다.

SSE의 `Last-Event-ID`는 재접속 cursor 전달 수단이고 서버의 기록 재생·DB 상태 복원·앱 반영 확인은 별도 구현이다. 이벤트 수신을 원입찰 판정 반영 확인으로 대체하지 않는다. 공개 이벤트/snapshot에는 비공개 최저낙찰가·낙찰자 식별·이메일을 넣지 않는다. [SSE 표준](https://html.spec.whatwg.org/multipage/server-sent-events.html)

**성공 기준:** 모든 지정 장애 사례에서 클라이언트가 DB의 현재 상품·최고가·최고입찰 상태·마감·중단/보류·확정 결과로 수렴한다. 오래된 이벤트에 의한 상태 회귀와 레인/상품 혼입 0건. 커밋된 변경은 재전송 또는 snapshot으로 복원되고, 롤백된 변경을 승인된 상태로 전파하지 않는다. 원요청 승인 사실과 현재 최고입찰/최종 낙찰은 구분한다. 느린 연결의 대기와 버퍼가 무한 증가하지 않으며 그 연결의 실패가 입찰 DB 트랜잭션을 막지 않아야 한다.

## 4. 성능·반복·측정 조건 제안

### 4.1 이미 승인된 목표

R-48/49: **4레인·동시 연결 100명, 기본 입찰 역할 20명·관람 역할 80명**. 클릭→본인 최종 승인/거절 표시 p95 ≤ 1초, 권위 있는 상태 확정→다른 화면 반영 p95 ≤ 1초, 연결 재수립→현재 상태 복원 p95 ≤ 3초. 정책 위반 승인·거절, 중복 처리 효과, 잘못된 낙찰은 각각 0건이다.

100명은 가입자 제한이 아니고 입찰자 20명이 각각 매초 입찰한다는 뜻도 아니다. API 응답·서버 송신·순수 HTTP 부하 측정만으로 화면 반영 목표의 통과를 선언하지 않는다. 이 목표는 승인된 시험 조건의 검증 목표이며 운영 최대 수용량이 아니다.

### 4.2 실행 전 승인받을 시험 조건 — OPEN-13

아래 값은 작은 실험을 위한 **제안값**이다. 운영 정책·운영 한계로 확정하지 않는다.

| 지연·유실 주입 | 시험 프록시의 추가 왕복 지연 100ms, 지정 응답/이벤트 유실·중복·역전. 기본 로컬 환경 결과와 구분 |
| 성능 측정의 시간초과 | 결과 표시 10초 / 재연결 복원 15초를 관측 중단 기준으로 제안. 원요청 거절·미확인 제한 해제·업무 장애 기준으로 사용하지 않음 |

| 확장 탐색 | 기본/집중 시험이 정확성을 통과한 뒤 200→400연결 등 단계 증가. 지연/queue lag의 악화나 자원 부족 시 중단. 운영 수용량은 추정하지 않음 |

공정한 비교를 위해 후보별 DB durability, pool·스레드·버퍼, 타이머·dispatcher 주기와 데이터 조건을 동일하게 기록한다. DB 내구성 설정을 낮춰 얻은 속도를 내구성 검증 통과로 해석하지 않는다. 얇은 실험 클라이언트는 공유 의도 등록→실제 입찰→최종 표시까지 실행하며 클릭 측정에 등록 왕복도 포함한다.

실험용 브라우저의 실제 DOM 반영 계측을 포함한다. 프로토콜 클라이언트로 만든 100연결 시험과 실제 브라우저 표본은 구분하고 각각 실제 연결 수·입찰 역할·관람 역할을 기록한다. 브라우저 측정이 없는 경우 R-49의 화면 p95는 NOT_RUN으로 남긴다.

클라이언트의 클릭/표시/재연결 간격은 단조 시계로 측정한다. 상태 확정→다른 화면 지연은 DB 권위 버전·트랜잭션 확인 시점·서버/클라이언트 시계 대응과 오차를 기록해야 한다. 클라이언트 간 wall clock을 검증 없이 빼지 않는다. 정확한 DB commit 시각을 확보하지 못하면 측정 경계를 proxy/상한으로 표시하고 권위 상태 확정 지연을 정확히 측정했다고 주장하지 않는다.

처리량, 접수/판정 큐 길이·최대 지연, 락 대기, 충돌/재시도, DB pool, CPU·메모리, dispatcher 적체, SSE 연결/버퍼, 레인별 지연을 함께 측정한다. 부하 발생기와 서버가 같은 PC면 경합이 결과에 섞이므로 별도 발생기 환경과 동일시하지 않는다.

## 5. 최소 기술 후보와 비교 조건

| 기술 | 우선 실험 후보 / 대안 검토 조건 |
| --- | --- |
| Spring MVC | REST 요청·조회·확인과 SSE 통지. JDBC 중심의 작은 실험 후보. 정확한 버전/JDK 호환성은 구현 전 확인·고정 |
| WebFlux | MVC의 느린 연결 쓰기·executor 포화가 실제 병목으로 측정되고 end-to-end 처리 모델의 이익이 필요한 경우 비교 |
| REST / SSE / WebSocket | 명령은 REST, 서버→화면은 SSE부터 비교. 지속적인 양방향 채널이 필요한 근거가 있으면 WebSocket 대안 검토 |
| PostgreSQL | 권위 접수 기록·공유 의도·원판정·경매 상태·outbox를 같은 DB 자원에 저장하는 후보 |
| 비관적 락 | 레인별 짧은 접수 직렬화와 판정 원자성을 검증하는 시작 후보. 공통 순서 보장은 별도 규약 |
| 낙관적 락 | 정확성은 동일 조건으로 유지하면서 충돌률·재시도 비용을 비교. 재시도로 원시각·순번 변경이나 후행 추월 허용 금지. E1 병목이 확인되면 최소 변형 비교 |
| Redis | 현재 실험의 필수 구성으로 제안하지 않음. 측정된 캐시/연결 공유 필요가 있을 때 역할과 장애 비용 검토. DB 원판정의 대체 저장소로 자동 채택하지 않음 |
| 메시지 브로커 | outbox dispatcher부터 검증. 독립 소비자·다중 서버 fan-out·재생/처리량 요구가 확인되면 비교. 도입 자체가 DB와의 원자성을 해결한다고 가정하지 않음 |

Spring MVC도 SSE를 지원한다. 비동기 요청을 사용해도 응답 쓰기는 blocking일 수 있으므로 느린 소비자·전송 executor·heartbeat를 측정한다. 현 단계에서 MVC/SSE가 지연 목표를 만족한다고 판단할 증거는 없다. [Spring MVC 비동기 요청](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)

한 경매의 순차 판정 구간은 한 상품의 집중 쓰기 처리량을 제한할 수 있다는 설계 추정이다. 서버 수를 늘려도 같은 레인의 직렬 구간이 자동으로 빨라진다고 기대하지 않는다. 네 레인의 논리적 독립성과 공유 DB·CPU·전송 자원의 성능 독립성을 구분한다. 다중 서버 구성에서는 다른 서버가 커밋한 상태도 각 서버의 구독 클라이언트에 도달하는지 별도 검증해야 한다.

## 6. 구현·증거 저장과 결정 기준

승인 후 코드는 `experiments/spike-001/` 같은 독립 위치에 둔다. 전용 빌드·DB·fixture·얇은 화면·장애 주입기를 사용하며 제품의 정식 구조에 편입하지 않는다. 실패 주입은 실험 실행 모드/loopback 범위에서만 동작하도록 한다. 실제 사용자 계정·상품 대신 무작위 메모리 fixture를 쓰고 비밀번호·토큰·세션은 출력하지 않는다. 인증·배포·완전한 제품 UI는 이 실험으로 검증됐다고 주장하지 않는다.

각 실행의 증거에는 RunId, 코드 hash, OS/JDK/프레임워크/PostgreSQL 버전, DB durability, 자원·pool·스레드 설정, 네트워크/발생기 위치, seed·반복 수·부하, **실제 실행 명령과 종료 코드**, 원시 요청/이벤트/상태 이력, DB 검증, 브라우저 계측, 정책 오류 수·실패 수·지연 분포를 포함한다. 비밀값은 제외한다. 실행하지 못한 항목은 원인과 NOT_RUN을 남긴다.

| 결과물 | 현재 상태 |
| --- | --- |
| 실험 목표·성공 기준·환경 조사·최소 후보 | 이 문서의 제안 |
| 실험 코드·실행 가능한 재현 스크립트 | NOT_IMPLEMENTED |
| 실제 테스트 명령·실행 결과·경쟁 요청 결과·성능 수치 | NOT_RUN |
| 운영 아키텍처 권고 확정 / 후속 ADR | 실험 증거 확보 뒤 결정 |

**이 spike의 종료 기준:** E1의 접수·마감 규약, E2의 원판정/공유 확인/복구 규약, E3의 이벤트·snapshot 병합이 동일한 불변식을 만족하는 실행 증거를 확보한다. 4레인/100연결의 합의 조건에서 정확성과 화면 지연을 함께 평가하고, 관찰한 병목·확장 한계와 미검증 범위를 기록한다. 실패하면 원인·반례·대안으로 설계 결정을 내릴 근거를 남긴다. 현재는 계획 단계이므로 종료 조건을 달성하지 않았다.

후속 아키텍처 결정 자료는 ① 접수/시간/마감 경계 계약 ② 논리적 원자성의 DB 구현 근거 ③ 중복·공유 확인·장애 복구 프로토콜 ④ 버전·outbox·재연결 계약 ⑤ 비관적/낙관적 락 비교 필요성과 비용 ⑥ MVC/SSE 및 Redis/브로커 필요 여부 ⑦ Aggregate B/C 및 소유 위치에 미치는 영향이다.

OPEN-09의 장애 감지·범위·마감 선후 증거, OPEN-10의 시간 정밀도·시계·기록 확정/복구·프로토콜, OPEN-13의 시험 조건은 결과로 좁혀야 한다. 전원 손실·디스크 손실·DB failover·외부망·여러 배포 노드·실제 운영 개인정보 보존은 별도 검증이 없으면 미검증으로 남긴다. 승인된 보류 정책을 임의 자동 종료 기능으로 바꾸지 않는다.

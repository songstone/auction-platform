기능 기대값의 원본은 [MVP-PRD](../product/MVP-PRD.md)의 AC이며, 불변식·도메인 사례·기술 주장은 [DOMAIN-MODEL](../architecture/DOMAIN-MODEL.md)의 INV/TS/TV다. API 스키마는 [OpenAPI](../../contracts/openapi.yaml), 전달·복구 의미는 [auction-events](../../contracts/auction-events.md), 현재 미정의 공식 원본은 [DECISION-LOG](../decisions/DECISION-LOG.md)다. 여기서 새 정책이나 성공 응답 스키마를 정의하지 않는다.

기존 `CONTRACT_STATIC_ONLY / PASS`, `DOCUMENT_STRUCTURE_ONLY / PASS`와 [SPIKE-001](../spikes/SPIKE-001.md)의 지정 관측은 기존 증거로만 참조한다. 새 제품의 health·컴파일·fixture 관측·합성 경계 사례를 실제 입찰·동시성·장애·성능 인수 통과로 확대하지 않는다.

## 2. 증거를 분리하는 단위

| 증거 분류 | 관측할 사실 | 대신할 수 없는 것 |
| --- | --- | --- |
| DOC_STATIC | 계획의 링크·ID·표·인코딩·공백 | 구현 실행·제품 기능 |
| BASELINE_INTEGRITY | 승인 manifest의 보호 파일 hash와 실제 bytes 일치 | 승인 범위 확대·생성 코드의 정확성·런타임 보안 |
| BUILD_ARCH | 컴파일·타입/생성 차이·패키지 의존성·배포 산출물 | 기능 AC·DB 트랜잭션·브라우저 동작 |
| PROCESS_HEALTH | 실제 프로세스 기동·운영 health의 상태/본문·종료 | 입찰 접수·DB/메일 readiness·실제 권한 집행 |
| DEV_PREVIEW | 개발 전용 고정 fixture가 실제 브라우저에서 렌더링된 관측 | 실제 회원/운영자 세션·서버 판정·SSE·네트워크 복구 |
| FUNCTIONAL | 정해진 입력/상태에서 업무 결과와 오류·무변경 조건 일치 | 같은 키 경합·commit 불명·실제 세션 |
| TRANSACTION | 실제 PostgreSQL의 commit/rollback·원기록·잠금·순서·경합 결과 | 메모리 mock의 성공·HTTP 응답 하나·물리 시각 보장 |
| SESSION_SECURITY | 실제 인증 세션·쿠키/CSRF·행위자/소유자/역할·권한 필터 | 스키마의 security 선언·가짜 로그인 fixture |
| NETWORK_REALTIME | 실제 HTTP/SSE 단절·유실·중복·순서·재생/live·snapshot/개인 복구 | 서비스 admission 장애의 범위/선후·DB 손실 복구 |
| FAILURE_RECOVERY | authority·old tx·DB/프로세스 장애·기록 불명·보류/재개 증거 | 단순 SSE 재연결·서비스 재기동 성공 |
| BROWSER_INTEGRATION | 같은 빌드의 실제 서버와 PC/모바일 브라우저 흐름·표시 | 지원 브라우저 전체 인수·DB/장애·성능 통과 |
| PERFORMANCE | 합의 환경/표본/측정 경계에서 지연 분포와 정확성 결과 | 운영 수용량·외부망/다른 배포 구성 보장 |
| OPERATIONS | 배포/백업/복원·비밀/개인정보·실거래 운영 준비의 실제 확인 | 설계 승인·로컬 컨테이너 기동 |

하나의 실행이 여러 분류의 증거를 만들 수 있으나 보고 항목은 분리한다. 실제 관측 대상·조건·한계를 기록하고 테스트 총수로 서로 다른 증거를 합치지 않는다.

## 3. 이번 골격의 초기 검증 범위

다음 `FND-*`는 이 QA 계획의 실행 항목 ID이며 제품 AC를 추가하지 않는다. 현재 빌드 도구 전환의 실행·관측·미실행은 [GRADLE-MIGRATION-VERIFICATION](GRADLE-MIGRATION-VERIFICATION.md), 초기 Maven 골격 실행은 [FOUNDATION-VERIFICATION](FOUNDATION-VERIFICATION.md)을 따른다. 실제 파일명·명령·산출물은 생성한 모듈의 실행 안내와 통합 스크립트에서 가져온다.

| 항목 | 실행·관측 | 기대값과 증거 | 제외 범위 |
| --- | --- | --- | --- |
| FND-01 승인 원본 | [승인 manifest](../../contracts/approved-baseline-0.1.0.json)의 보호 파일을 실제 bytes로 비교 | 승인된 파일 hash 불변. 불일치 파일·기대/실제 hash·명령 exit code를 기록 | 승인 전 snapshot·과거 증거와 현재 approvedFiles의 역할을 구별. 새 hash 자동 승인 금지 |
| FND-02 개발 진입 | 필요한 JDK/빌드/Node/패키지 도구 확인, 로컬 인프라 구성과 시작/종료 명령 실행 여부 확인 | 선택한 정확 버전·환경 변수 이름·의존 서비스 상태 기록. 비밀 원문 출력 없음 | 컨테이너 시작을 migration·세션·입찰의 성공으로 판정하지 않음 |
| FND-03 BE 빌드 | backend의 실제 빌드·검사 명령 | Java 25/Spring 골격이 빌드됨. 결과·로그·시험 범위·실패/skip 수 보존 | 제품 command/query·전체 AC 완료 아님 |
| FND-04 BE 의존성 | 모듈/계층 아키텍처 검사 | 도메인의 Spring/JDBC/HTTP 직접 의존과 순환 등 구현된 규칙 확인. 빈 패키지/미검사 규칙도 명시 | 비어 있는 도메인의 PASS로 미래 업무 코드의 경계 준수를 보장하지 않음 |
| FND-05 BE health | 실제 앱 기동 후 운영 health 호출·프로세스 종료 | 실제 HTTP status·본문·시각·빌드 식별과 DB 연결 여부 기록 | 업무 API·입찰 가능 상태·DB/메일 정상 여부를 검사 범위 이상으로 추론하지 않음 |
| FND-06 FE 생성 | 봉인 OpenAPI로 타입 재생성·diff·타입 검사 | 같은 계약 입력에서 생성물이 재현되고 금액/counter/ID wire 타입을 임의로 바꾸지 않음 | TypeScript 타입만으로 런타임 JSON·업무 권한 집행이 검증되지 않음 |
| FND-07 FE 빌드/경계 | frontend 검사·production build와 개발 전용 진입 설정 확인 | 빌드 결과·fixture의 개발 전용 표시와 배포물 포함/노출 상태를 실제 구성에 맞게 기록 | fixture가 프로덕션 세션/입찰/SSE인 것처럼 보이지 않음 |
| FND-08 브라우저 미리보기 | 실제 브라우저에서 고정 fixture 미리보기 진입 | fixture 표시, 공개 상태/유찰 필드 경계, 렌더링·콘솔 오류 관측을 기록 | 실제 서버 연동·반응형 전체·지원 브라우저 인수 아님. 브라우저 미실행이면 NOT_RUN |
| FND-09 문서 추적 | 두 계획 UTF-8·로컬 링크·표·AC/INV/TS 참조·공백 | 참조한 공식 ID 존재, 카드와 QA 범위 연결, 오래된 PASS 전용 방지 | 제품 실행 검증 아님 |

Gradle 전환에서는 FND-03/04/05를 새 빌드 도구와 `build/libs/auction-platform-backend-0.1.0-SNAPSHOT.jar`로 구분해 확인한다. Windows 명령은 `backend/`에서 `.\gradlew.bat --no-daemon clean build`, Unix 명령은 `bash ./gradlew --no-daemon clean build`다. `build/test-results/test/`의 XML·`build/reports/tests/test/`의 보고서·패키징 JAR 관측을 새 실행에 연결하고 Maven의 과거 보고서/시험 수로 재사용하지 않는다. Boot 3.5.16의 공식 Gradle 7/8 지원 표와 JDK 25 실행에 필요한 Gradle 9.1 이상을 구분하며, 선택한 Gradle 9.8.1의 실제 성공이 Boot의 공식 지원을 확대하지 않는다. 근거와 설정은 [backend 안내](../../backend/README.md)를 따른다.

FND-06~08에서 사용하는 금액·시각·상태는 계약의 기존 예제 또는 승인 스키마에 맞는 합성 자료다. 예시 값을 금액 상한·입찰 단위 후보 목록·일정 입력 정밀도·사진 제한·세션 수명으로 채택하지 않는다. 실제 DB가 없는 골격에서도 실행 가능한 검사와 DB가 있어야 하는 검사를 명령/보고에서 구별한다.

## 4. 제품 QA 우선순위와 추적성

아래 `QA-*`는 후속 제품 인수 작업 묶음이며 인수 원본을 대신하지 않는다. P0는 잘못된 입찰·결과·권한·복구를 막는 우선순위, P1은 정상 운영과 이용 흐름, P2는 합의된 환경에서의 성능/운영 판단 순서다. 아래 제품 인수 사례는 현재 **NOT_RUN**이며 이번 골격의 실행 결과와 구별한다.

| --- | --- | --- | --- |
| QA-01 / P0 입찰 계산 | 시작가를 가상 Bid로 세지 않음, 정확한 다음 금액·본인/최고자 제한, 최저 미달/같음/초과, 비정렬 최저가 허용 | AC-R09-01, AC-R10-01, AC-R17-01, AC-R18-01, AC-R46-03; INV-06/10~12/15/22; TS-01~08 | FUNCTIONAL의 순수 규칙과 실제 HTTP 업무 결과를 구별. OPEN-05 상한/후보는 보류 |

| QA-12 / P2 운영 | 배포·재기동·복원·원기록 보호·비공개 파일·비밀·개인정보/실거래 안내 | AC-R23-13, AC-R24-05, AC-R43-01, AC-EX01-01; INV-23/28/39/40/46 | OPERATIONS. OPEN-12/14 등 운영 결정 후 판단. 로컬 골격 준비로 운영 가능성 선언하지 않음 |

초기 제품 수직 흐름은 QA-01/03/04/06을 우선 묶는다. 등록→실접수→원승인/원거절→자동 ACK→같은 키 조회에서 실제 저장과 권한을 확인하고, 이어 QA-02/05/07/08의 시간·경합·복구를 넓힌다. 이 순서는 P1 회차 기반을 무시하거나 승인되지 않은 운영 값을 임시 정책으로 넣으라는 뜻이 아니다.

## 5. 트랜잭션·세션·장애 시험의 구체 경계

### 5.1 실제 DB와 순서

| 경계 | 필요한 관측 |
| --- | --- |
| 등록과 실제 접수 | 공유 등록 확인·원경매/금액 결합, 실제 접수 전 순번/입찰 승인 부재, 다른 기기의 같은 의도 인계 |
| 접수 tx | gate 이후 원시각·범위별 순번·원내용을 함께 저장. rollback 후 외부 공식 접수 없음. commit 결과 불명은 같은 키 원기록으로 확인 |
| 판정 tx | 선행 순번·현재 구간/마감과 원판정, 승인 Bid/최고가/단계/마감/공개 버전/outbox의 부분 효과 없음 |
| 상위 범위 재진입 | 마지막 레인 종료 등에서 역순 lock/부분 commit 없음. 재진입 뒤 원내구 접수 시각·순번 보존 |
| Round와 일정 | 모집 중복·공개/배정·시작/취소의 별도 순서, 공개 Auction 생성·단일 진행 점유·동시 마지막 레인 완료 |
| 원키와 ACK | 회원/운영자 이름공간의 내용 결합·효과 1회, ACK가 해당 원판정/의도에만 작용, 다른 레인의 같은 키 경합 |

관련 실행 사례는 [ADR-002](../decisions/adr/ADR-002-DURABLE-RECEIPT-AND-ORDERING.md)의 RC-01~12와 연결한다. RC는 이미 통과한 시험이 아니라 필요한 실행 후보이다. 구체 SQL·고유 제약·잠금 그래프·격리 수준의 정확성은 구현 후 증명한다.

### 5.2 실제 세션과 정보 경계

- 비회원·이메일 미검증·가입 완료 회원·다른 회원·사전 지정 운영 전용 계정의 실제 세션을 구분한다. 쿠키/CSRF 없는 변경 요청과 타인 원키/사진/개인 목록 접근을 각각 확인한다.
- 동일 회원 두 기기에서 등록·조회·원판정 수신/반영·ACK를 관측한다. 모든 기기 확인을 요구하지 않고, 어느 기기의 일치 확인이 해당 공유 제한만 해제하는지 검증한다.
- 세션 종료·만료·재인증의 실제 경로에서 원입찰/원판정과 미확인 제한을 보존한다. 만료 시간이나 재설정 후 기존 세션 무효화 여부는 OPEN-06 결정 전 임의 기대값으로 만들지 않는다.
- 공개 응답·snapshot·SSE·로그를 따로 확인한다. `NO_SALE` 결과에서 최고입찰가를 숨기면서 본인 원입찰 금액·원판정을 보존하는지 대조한다. 낙찰자 식별 상세와 추가 운영자 조회는 deferred 범위를 유지한다.

### 5.3 네트워크와 서비스 장애

| 주입/관측 | 기대 구분 |
| --- | --- |
| 접수/원판정/ACK 응답 유실·개인 조회 실패 | 원키 복구. NOT_FOUND·timeout·연결 성공만으로 원거절/확인 완료를 추정하지 않음 |
| SSE 단절·재생/live 겹침·중복·공백·마지막 유실 | snapshot과 scope/세대별 순서로 복원. 공개 SSE 성공은 개인 원판정 확인이나 서비스 재개 증거가 아님 |
| 앱/DB/authority 연결 손실·old worker 정지/재개 | 영속 권위와 기존 tx 결말·원기록·보류 범위/선후 확인. 자동 takeover·자동 재개를 추가하지 않음 |
| 완전 미결 이력·권위 이력 불명·복구 불능 | 완전 이력은 원순서 판정, 불명은 보류. 미접수 종료·가상 유찰·강제 취소로 정리하지 않음 |
| 정상 callback 지연·새 마감 후 장기 판정 지연 | 기존 경계 유지와 결과 보류를 구분. 뒤늦은 처리 시각+후속 시간으로 원마감을 바꾸지 않음 |
| 재개 응답 유실 뒤 새 중단·옛 재개/확인 재도착 | 원결과·원 R 보존, 새 중단 해제/시간 재부여 없음 |

전이 시간은 [ADR-001](../decisions/adr/ADR-001-TRANSITION-TIME.md)의 TM-01~09, 권위·장애 복구는 [ADR-003](../decisions/adr/ADR-003-FAILURE-AUTHORITY-AND-RECOVERY.md)의 FA-01~14를 추적한다. 실제 S/N/R 취득·projection/추가 commit 간격·접수 연속성, old tx의 확정 권한은 미완성/미검증이다. 기록된 PostgreSQL commit timestamp·COMMIT 응답·실제 활성화·물리 내구 완료를 같은 관측점으로 합치지 않는다.

필요한 결함 주입은 격리 시험에서만 제공하고 운영 업무 API로 노출하지 않는다. 승인된 의미를 구현하며 필요한 시험을 실행하는 방식으로 진행할 수 있으며, 별도 SPIKE 완료만을 착수 조건으로 강제하지 않는다.

## 6. OPEN에 따른 보류 사례

아래는 QA의 보류 적용 예시다. OPEN 자체를 수정·해결 처리하는 원본은 DECISION-LOG다. 수치 제안·스크립트 timeout·도구 기본값을 제품 정책으로 사용하지 않는다.

| 잔여 결정 | 지금 검증 가능한 것 | 보류할 합격 기준/사례 |

`BLOCKED_POLICY`는 해당 값이 미정인 경우, 미구현은 `NOT_IMPLEMENTED`, 실행하지 않음은 `NOT_RUN`, 실행 환경 부재는 `BLOCKED_ENV`, 실행된 기대값 위반은 `FAIL`로 구분한다. 미완성 메커니즘을 정책 미정으로 돌리거나, 정책 보류 사례를 실행 통과율에서 누락하지 않는다.

## 7. 성능의 측정 약속과 실제 운영 경계

R-48/49의 목표는 기존 승인 그대로다. 기본 구성은 4레인·동시 연결 100명(입찰 역할 20명/관람 역할 80명), 집중 입찰은 별도 시나리오다. 100명을 서비스 가입자/접속 상한으로 구현하지 않는다. OPEN-13을 통해 환경·빈도·지속·반복·집중 패턴·실패 처리·산정법을 정한 뒤 실행한다.

| 목표 | 실제 측정 경계와 보고 |
| --- | --- |
| 입찰 응답 p95 ≤ 1초 | 클릭 → 본인 승인/거절 화면 반영. 접수 202 도착을 최종 판정으로 세지 않음 |
| 전파 p95 ≤ 1초 | 서비스의 권위 있는 상태 확정 → 다른 참가자 화면 상태 반영. outbox 기록/큐 삽입까지만 측정한 수치와 분리 |
| 복원 p95 ≤ 3초 | 연결 재수립 → 현재 상태 복원. 실제 중단/보류 상태를 유지하고 자동 재개를 성공으로 세지 않음 |
| 정확성 | 합의 시나리오에서 정책과 다른 승인/거절·중복 효과·잘못된 낙찰 각각 0건. 실패·미완료·불명 표본 수와 취급 공개 |

브라우저 수신과 화면 반영을 관측하지 않은 load harness 값은 해당 내부 구간의 수치로만 보고한다. 이미 선택한 wire 시각 정밀도는 실제 시계 정확도 보장이 아니며 서로 다른 프로세스/시계의 측정 오차를 기록한다. 기존 loopback SPIKE 결과를 새 제품·외부망·운영 수용량으로 재사용하지 않는다.

## 8. 실행 기록 양식과 완료 판정

각 실행에는 다음 정보를 남긴다. 보안 토큰·세션 쿠키·비밀번호·실제 거래 연락 이메일은 원문 증거에서 제거한다.

| 필드 | 기록 내용 |
| --- | --- |
| 실행 식별 | 카드/QA/FND ID, 실행 ID·UTC 시각, 담당, 증거 분류 |
| 대상 | commit 또는 dirty diff 식별·앱 산출물 hash·계약 버전/승인 hash·도구 버전 |
| 환경 | OS·JDK/Node/DB·프로필·네트워크·실행 토폴로지·합성 데이터/시계·주입 지점 |
| 절차 | 정확 명령·준비/정리·입력/사건·해당 OPEN 결정 또는 보류 사유 |
| 기대/관찰 | 연결 AC/INV/TS/TV·실제 응답·DB/원기록·이벤트/화면·로그/추적·오류/timeout |
| 결과 | PASS/FAIL/NOT_RUN/NOT_IMPLEMENTED/BLOCKED_POLICY/BLOCKED_ENV, 수량·실패/skip·미관측 범위 |
| 인계 | 결과 파일/로그/화면 증거 위치·잔여 위험·후속 카드 |

실행물/명령/원시 증거가 없는 항목은 PASS로 바꾸지 않는다. 하나의 버그 수정 뒤 영향 검사를 수행하고, 새 변경·실패·미해결 우려가 없는 상태에서 전체 시험을 반복하는 것을 완료 조건으로 추가하지 않는다.

현재 Gradle 전환의 수행 여부·정확 명령·증거·검사 수·미실행은 [GRADLE-MIGRATION-VERIFICATION](GRADLE-MIGRATION-VERIFICATION.md)에 기록하며, 초기 Maven 실행은 [FOUNDATION-VERIFICATION](FOUNDATION-VERIFICATION.md)에 이력으로 보존한다. 여기에는 별도의 현재 상태 표나 결과 숫자를 복제하지 않는다. 골격의 실제 DB 연결 관측은 제품 트랜잭션·인증 세션 검증과 구별하고, 개발 fixture의 브라우저 관측도 실제 경매 연동·재접속·장애·성능 인수와 구별한다. 기존 승인 문서/계약 정적 검사와 SPIKE는 기존 범위의 증거이며 새 제품 QA 통과로 합산하지 않는다.

현재 범위 완료는 FND 실행 결과와 남은 미실행을 구분해 기록하는 것이다. 제품 전체 완료는 구현된 기능별 AC·불변식·경합/복구·권한·브라우저·성능 증거와 미정/제외 범위를 별도로 대조해야 한다. 계약 불일치는 구현에서만 보정하지 않고 [ADR-005](../decisions/adr/ADR-005-CONTRACT-BASELINE.md)의 변경 절차로 인계한다.

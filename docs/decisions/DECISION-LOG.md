## 1. 기존 기록과 이번 승인 관계

기존 문서는 참고 자료로 사용했으며, 이번 대화에서 다시 확인한 정책을 현행 기준으로 삼았다. 이전 원문은 Git 커밋 `018f56521179103542e348df75beac28602492c2`의 `docs/decisions/DECISION-LOG.md`에 보존되어 있다. 해당 커밋의 제품 개요와 경매 규칙도 같은 기준의 참고본이다.

기존 `D-001`~`D-041`은 주제와 식별자를 유지하면서 아래 현행 결정으로 갱신했다. `D-042`는 과거 문서에 적힌 승인·작성 이력으로 남기며, 현재 승인은 `D-054`에 별도로 기록한다. 기존본에만 있는 세부 정책을 이번 승인으로 자동 승계하지 않는다.

## 4. 현재 검토 중인 제안

다음 네 문단은 **D-095 이전의 검토·초안 작성 이력**이다. 당시의 미승인 상태와 현재 구현 기준선 채택을 혼동하지 않으며 현재 상태는 D-095와 아래 표를 따른다.

2026-10-15 P0 기술 검토의 [ADR 목록](adr/README.md)을 초안으로 추가했다. 그 초안 작성 지시는 설계 채택·제품 정책 변경·공통 계약 확정의 승인이 아니었다. 당시 선택지·추천·검증 조건은 각 ADR이 원본이며 D-091과 미선택 상태를 유지했다.

같은 날 사용자의 시스템 설계 단계 진행 지시에 따라 [SYSTEM-DESIGN](../architecture/SYSTEM-DESIGN.md)의 당시 0.1과 [ADR-004](adr/ADR-004-MVP-STRUCTURE.md)를 초안으로 작성했다. 추가 실험을 설계·계약 초안 작성의 선행조건으로 두지 않았다. 미검증 가정·위험을 공개한 설계/계약 채택은 사용자 승인으로 판단하며 실제 구현·정확성·성능·장애 보장은 실행 증거와 별도로 구분했다. 당시 설계·기술·공통 계약은 미승인 상태였다.

후속 진행 지시로 [OpenAPI](../../contracts/openapi.yaml)·[이벤트 계약](../../contracts/auction-events.md)·[계약 안내](../../contracts/README.md)와 [ADR-005](adr/ADR-005-CONTRACT-BASELINE.md)를 `0.1.0-draft.1` 초안으로 추가했다. 알려진 업무 계약은 구체화하고 입력·계정·조회·운영의 잔여 OPEN과 미정 표면을 표시했다. 그 작성 지시는 기술 채택·공통 계약 확정 승인이 아니었으며 당시 D-091과 기존 OPEN의 승인 상태를 유지했다. 실제 서비스·DB·네트워크·브라우저·장애·성능 검증과 계약 정적 검사는 별개였다.

다음 단계로 [CONTRACT REVIEW 001](CONTRACT-REVIEW-001.md)에 결정 우선순위·추천안·정확한 계약 영향·부분 채택 범위를 정리했다. 이후 CR-01~03의 운영자 겸용·최저낙찰가 정렬·유찰 종료 가격 공개 질문에 대한 명시 답변만 D-092~D-094로 승인 기록했다. 그때는 CR-04~10·SEC·T의 수치·보안 세부·설계 채택과 공통 계약의 최종 승인을 별도로 남겼다. 이후 T의 방향/원칙과 정의된 계약만 D-095로 채택했으며 CR-04~10·SEC와 잔여 OPEN의 미승인은 유지한다.

## 8. 후속 변경 원칙

1. 승인 요구사항의 의미를 바꾸려면 관련 R/D ID, 변경 이유, 대안, 인수 조건 영향을 제시하고 제품 책임자의 승인을 받는다.
2. OPEN은 결정 근거·승인일을 기록한 후 해결 처리한다. PROP 채택과 HYP 검증은 각각 정책 승인·실행 증거와 구분한다.
3. 변경 시 [제품 개요](../product/PRODUCT-BRIEF.md), [MVP PRD](../product/MVP-PRD.md), [경매 규칙](../product/AUCTION-RULES.md), 이 기록을 함께 맞춘다.
4. 대체 시 이전 근거와 대체 관계를 남긴다. 과거 기록을 현행 정책 근거로 오인하지 않게 한다.
5. 이후 검증 결과는 대상·조건·관찰 결과·미검증 범위를 기록한다. 문서 정적 검토, 구현 검증, 실제 운영 증거는 서로 대체하지 않는다.

## 1. 결정 목적과 원본의 범위

백엔드·프런트엔드·QA가 독립적으로 설계·구현할 구조·기술·소유권을 정의한다.
초안 작성 당시 추가 실험을 선행하지 않고 설계를 진행했고, D-095로 남은 OPEN·미검증 위험을 유지한 현재 구조와 정의된 API·이벤트를 구현 기준선으로 채택했다.
이 채택은 운영 성능·장애 안전성의 검증 완료나 미정 정책의 확정을 의미하지 않는다.

- 요구사항·인수 조건의 원본은 [MVP PRD](../../product/MVP-PRD.md), 승인 이력·OPEN의 원본은 [DECISION-LOG](../DECISION-LOG.md)다.
- 도메인 책임·논리적 원자성의 승인 기준선은 [DOMAIN-MODEL](../../architecture/DOMAIN-MODEL.md) §4~6이다. B/C·생성 시점은 현재 미선택이다.
- 모듈 책임·의존성 표와 실제 시스템 흐름의 공식 원본은 SYSTEM-DESIGN이다. 이 ADR은 선택 이유·대안·확장 제약을 소유한다.
- 경로·요청/응답 필드·이벤트 스키마는 이후 공통 계약 파일을 원본으로 삼는다. 이 ADR에서 같은 스키마를 재작성하지 않는다.

## 2. 채택한 구조와 기술 선택

**채택한 구현 기준:** Java 25·Spring MVC·JDBC의 모듈형 모놀리스, 단일 앱 인스턴스와 단일 권위 PostgreSQL, React·TypeScript 화면, REST 명령·조회와 공개 SSE 전파다.
하나의 DB 자원에서 필요한 상태를 함께 확정해 초기 분산 트랜잭션·노드 간 진행 권한 조정의 범위를 줄인다.
단일 활성 진행 주체 안에서 레인별 worker는 독립 실행할 수 있다. 모든 입찰을 전역 단일 순서로 묶지 않는다.
초기 앱 정지 시 서비스 가용성이 떨어지고, 수평 확장·자동 failover·무중단 배포를 보장하지 않는 초기 제한을 유지한다.

| 선택 | 해결하는 문제와 이유 | 대안·비용 / 선택 상태 |
| --- | --- | --- |
| 모듈형 모놀리스 | 같은 프로세스·DB 트랜잭션에서 입찰·제어·다음 전환의 불변식을 유지하며 모듈 책임을 나눔 | 마이크로서비스는 독립 배포 장점이 있으나 원자성·장애·전파 조정이 늘어 초기 추천에서 제외 |
| Java 25 + Spring MVC | 기존 spike의 실행·컴파일 기반을 이어 REST/SSE와 명시적 동기 DB 처리를 구성 | 제품 실행 기준 채택은 D-095가 근거. 프레임워크·JDK 세부 버전은 구현 준비 때 호환성 확인·고정 |
| JDBC | 레인 gate·원접수·순번·원판정·outbox의 SQL과 트랜잭션 경계를 직접 드러냄 | JPA도 가능하나 별도 비교 미실행. 매핑 편의와 잠금/조회 의미를 추가 검증해야 함 |
| 단일 권위 PostgreSQL | 원접수·공유 의도·경매 효과·원판정·outbox를 같은 저장 자원에서 보호 | 공용 DB/pool 경합·단일 장애점이 남음. replica·분산 저장으로 정확성이 자동 개선되지 않음 |
| React + TypeScript | 4레인 상태·본인 요청 처리 상태·재동기화 상태를 구분하고 화면 구성과 계약 타입을 연결 | 다른 UI 도구와 성능 비교 미실행. 타입은 런타임 검증·서버 판정을 대체하지 않음 |
| REST + SSE | 쓰기 명령·원키 조회/ACK와 서버→화면 상태 전파를 분리 | WebSocket의 양방향 지속 채널은 현재 필요 근거가 없음. WebFlux 전환도 성능 처방으로 확정하지 않음 |
| DB outbox | 상태 commit 뒤 전파 프로세스가 종료돼도 복원할 기록을 같은 tx에 보존 | broker를 쓰더라도 DB와의 원자성은 별도 문제. 초기에는 DB 조회 기반 dispatcher 후보 |

React의 TypeScript 지원은 [공식 안내](https://react.dev/learn/typescript)를 참고한다. 화면 간 공유 상태를 두는 선택은 [상태 공유 문서](https://react.dev/learn/sharing-state-between-components)에 맞춰 설계할 수 있다.
Spring MVC의 SSE도 실제 응답 쓰기는 blocking일 수 있으므로 느린 연결·전송 자원은 별도 검증한다. [Spring MVC 비동기 요청](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html)
Redis·메시지 브로커·WebFlux·WebSocket·별도 조회 DB는 초기 필수 구성으로 선택하지 않는다. 실측 문제와 필요한 역할이 생기면 별도 ADR로 비교한다.

## 3. Aggregate C안의 조건부 소유권

**조건부 채택 C:** Round·Lane·Lot·Auction을 분리하고 Bid·Result는 Auction 내부 변경 권한에 둔다. 필요한 교차 변경을 같은 DB 트랜잭션·보호 규약으로 묶는 조건을 유지한다. B로 바꾸려면 영향·반례를 제시하는 변경 절차를 따른다.
Round는 일정·공개·고정 시간·회차 시작/완료 조건, Lane은 현재 대상·진행 순서·수동/장애 원인과 중단 발생 건을 책임진다.
Lot은 출품자·최초 등록·상품/가격 조건·수정/취소 가능성을, Auction은 입찰 단계·최고입찰·마감·확정 결과를 책임진다.
Bid는 승인된 입찰의 불변 기록이고 Result는 Auction이 보호하는 배타적 결과다. 별도 변경 서비스로 Auction 검증을 우회하지 않는다.
도메인 객체마다 별도 서비스·DB를 만든다는 뜻이 아니다. 물리적 저장·인덱스·클래스와 Aggregate의 변경 권한은 구별한다.

| 비교 | 이유·장점 | 비용·선택 조건 |
| --- | --- | --- |
| B: Lane이 현재 Auction·입찰·결과를 소유 | 현재 상품 진행·중단·다음 전환의 조정을 한 경계에서 설명하기 쉬움 | 과거 Auction 소유·조회와 현재 그래프 크기를 명확히 해야 함. 여전히 유효한 대안 |
| C: 생명주기별 소유권 분리 | 과거 Auction의 안정된 식별과 현재 Lane 진행, Lot 출품, Round 일정을 각각 설명하기 쉬움 | 교차 Aggregate 조정이 늘며 같은 tx·보호 규약이 필수. 조정 비용이 이익보다 크면 B로 재검토 |

C가 B보다 빠르다는 실행 근거는 없다. 레인 gate가 같은 이상 소유권 분리만으로 한 레인의 직렬 구간이 사라지지 않는다.
Round 전체를 매 입찰 수정하거나 과거 Bid 전체를 매번 로딩하도록 만들지 않는다. 현재 최고값과 신규 불변 기록의 일관성을 보호한다.

## 4. 회원×Auction 참여 상태의 분리

공유 의도·미확인 제한·앱 확인은 회원 전체나 공개 경매 상태에 합치지 않고 회원×Auction의 독립 상태로 관리하는 안을 채택했다.
이는 최고가·마감·낙찰 판단과 다른 생명주기를 갖고 복수 기기에서 하나의 미확인 의도를 조정해야 하기 때문이다.
같은 회원의 다른 경매·다른 레인이나 같은 경매의 다른 회원을 이 제한으로 막지 않는다.
의도 등록·원키 내용 결합·실제 접수 연결·원최종 판정 ACK에 필요한 경쟁은 같은 DB의 고유성·트랜잭션 규약으로 보호한다.
등록과 실제 접수는 구별하며 등록에 공식 접수 순번·시각·가격 효과를 주지 않는다. 상세 프로토콜·원본은 ADR-002를 따른다.
참여 상태의 독립 관리는 새 분산 서비스·Redis 저장 선택이 아니다. auction 기능 안의 별도 변경 책임으로 시작한다.

## 5. Auction 생성 시점 — 공개 확정 시 채택

**채택한 생성 시점:** 공개 경계에서 선행 요청을 정리하고 유효 출품의 공개 조건·배치가 고정될 때 대기 중 Auction을 생성한다. 실제 원자 생성·부분 실패 복구는 구현 검증 대상이다.
출품 등록 때 생성하면 공개 전 수정·재배정마다 두 상태를 맞춰야 하고, 준비 진입 때 생성하면 공개 후 안정된 경매 식별을 별도로 마련해야 한다.
공개 확정 시 생성은 공개 후 상세 조회·참여 의도·원대상 식별의 기준을 미리 두는 이점이 있으나 공개 작업의 크기·복구 비용이 늘 수 있다.

1. 공개 직전 공식 접수된 유효 등록·수정·레인 수 변경을 원순서로 반영한 뒤 공개 조건·배치를 고정한다(D-081).
2. 그 전에 취소된 Lot에는 Auction을 생성하지 않는다. Lot 취소 이력은 유지하며 가상의 Bid·Result를 만들지 않는다.
3. 유효 Lot과 생성 Auction의 관계·공개 고정 조건 버전을 원자적으로 연결한다. 부분 공개·중복 생성은 허용하지 않는다.
4. 공개 정각에도 상품의 개시 전 취소 자격을 별도로 판단한다. 공개됐다는 이유만으로 출품자 취소를 일괄 거절하지 않는다.
5. 공개 후 상품 취소는 Lot의 표시·대상 제외와 해당 Auction의 진행 불가 상태를 같은 보호 규약으로 맞춘다.
6. 공개 후 회차 취소는 D-085의 미진행 표시와 원개별 취소 이력을 유지한다. 가상의 개별 취소 명령·입찰·낙찰/유찰 결과를 생성하지 않는다.

가격 조건의 원본은 공개 고정본 하나로 유지하고 Auction은 그 식별·버전을 사용한다. 필요 시 저장하는 불변 복사본도 독립 수정 권한을 갖지 않는다.
개시·준비는 Auction 레코드 생성과 다른 사건이다. 생성 시각을 실제 회차 시작 S·다음 준비 N·재개 R로 사용하지 않는다.
공개 일괄 처리의 실제 트랜잭션 크기·잠금·복구는 후속 검증 대상이며, 대량 공개 처리량을 보장하지 않는다.

## 6. 여러 Aggregate의 필수 원자성

Aggregate를 나눴다는 이유로 각각 commit한 뒤 이벤트로 핵심 경매 상태를 뒤늦게 맞추지 않는다.
애플리케이션 조정자는 필요한 도메인 판단을 호출하고 같은 PostgreSQL 트랜잭션과 공통 보호 규약으로 함께 저장한다.

- 입찰: Lane의 대상·중단·권한과 Auction의 단계·가격·시간을 검증하고 승인 Bid·최고입찰·마감·원판정·outbox를 함께 보호한다.
- 출품자/운영자 상품 취소: 원 Lot/Auction·자격·선행 요청·결과 없음·운영자 취소 사유와 Lane 대상 제외/다음 처리를 함께 보호한다. 출품자 취소에 필수 사유 입력을 추가하는 결정은 아니다.
- 중단·재개: Lane의 원인·발생 건과 Auction의 보존 단계·시간, 명령 원결과·원 R을 같은 변화로 설명해야 한다.
- 마감·다음 전환: 선행 입찰과 현재 마감을 확인해 유일한 결과, 현재 대상 해제, 다음 준비 또는 레인 종료의 부분 성공을 막는다.
- 회차: 공개 고정·배정, 실제 시작의 공통 S·운영 레인 초기화, 마지막 레인 종료와 회차 완료·진행 점유도 해당 공유 경계를 보호한다.

잠금 획득 순서를 업무 순서로 취급하지 않는다. 공식 접수·순번은 ADR-002, 전이 확정 시각은 ADR-001, 장애 진행 권한은 ADR-003이 원본이다.
다음 준비를 별도 내부 처리로 구성하더라도 이전 마감으로 소급하지 않고 권위 전이·재시작 복원을 설명해야 한다.
원자성·락 순서·불명 commit 복구가 미검증인 상태를 시스템 설계의 가정·위험으로 표시하고 문서 작성을 진행한다.

## 7. 기능 모듈과 계층 규칙

기능 모듈은 `identity`, `listing`, `auction`, `query`, `realtime`, `bootstrap`을 사용하며 책임·의존성 표는 SYSTEM-DESIGN만 원본으로 둔다.
모듈 내부는 순수 규칙, 애플리케이션 조정, 포트·어댑터를 구분하되 모든 작은 기능에 동일한 파일 수·접미사를 강제하지 않는다.
업무 엔티티는 D-096에 따라 JPA 매핑을 겸한다. 업무 메서드는 HTTP·Spring 서비스·Repository 호출·JDBC·현재 시각 조회·네트워크 발행에 의존하지 않고 검증된 행위자·공식 시각·상태를 입력받는다.
애플리케이션은 권한 맥락·원키·정합 상태 확보·도메인 호출·저장·원결과 응답을 조정하고 필요한 트랜잭션 경계를 소유한다.
기능별 서비스가 같은 기능의 Spring Data Repository를 직접 사용한다. 시계·파일·메일·명시 SQL 등 별도 기술 협력은 필요에 맞게 유지하며 단순 CRUD를 위한 매퍼·위임 어댑터는 두지 않는다.

출품의 회차 귀속·배정·공개·진행 취소처럼 여러 기능이 필요한 조정은 auction 애플리케이션에서 listing의 공개 포트를 호출하는 안을 사용한다.
listing의 순수 Lot 규칙은 listing에 두며, 이 조정을 위해 listing이 auction 내부로 되호출하는 순환 의존을 만들지 않는다.
참여하는 공개 변경 포트는 호출자의 같은 DB 트랜잭션에 합류해야 하며 내부에서 별도 commit하는 구현으로 필수 원자성을 깨지 않는다.
모듈 간에는 명시적인 공개 API·불변 입력/결과를 사용한다. 타 모듈의 내부 엔티티·저장소·테이블 변경을 직접 호출하지 않는다.
query의 권한별 읽기 모델은 쓰기 불변식을 우회하는 변경 통로가 아니다. realtime은 원판정을 바꾸거나 도메인 결정을 재실행하지 않는다.
bootstrap은 조립·설정·실행 진입을 맡고 업무 조정을 숨기는 공용 서비스 모듈로 키우지 않는다. 최종 의존성 그래프는 비순환이어야 한다.

## 8. 판정·조회·전파의 분리

상태와 outbox를 같은 tx에 저장하고 dispatcher가 commit된 기록을 별도로 읽어 연결에 전달하는 방향을 채택했다.
단순 after-commit 메모리 callback만으로 영속 전파를 대체하지 않는다. callback과 앱 종료 사이 유실은 outbox·snapshot 경로로 복구해야 한다.
공개 SSE는 버전이 있는 공개 상태 전파에 사용한다. 공개 상태 이벤트 수신을 본인 원입찰 판정 수신·반영 ACK로 간주하지 않는다.
본인 원판정·미확인 의도는 인증된 REST 조회·동일 키 재전송·앱 ACK를 우선 사용한다. 개인 SSE·개인 이벤트 outbox는 이번에 선택하지 않는다.
조회 상태·원판정·ACK·stream cursor는 별개 사실이다. 공개 payload에 원회원 키·비공개 최저 원금액·권한 밖 식별을 넣지 않는다.
느린 연결은 bounded buffer·연결 종료·재동기화 후보로 다룬다. 네트워크 송신·클라이언트 ACK를 입찰 DB tx에서 기다리지 않는다.
조회 폭주가 접수·판정 DB 접근을 소진하지 않도록 자원 보호를 설계한다. pool 증설·캐시·브로커의 효과를 검증 없이 단정하지 않는다.

## 9. 확장 제약과 검증 시점

기존 [SPIKE-001 §7~8](../../spikes/SPIKE-001.md#7-실시간브라우저성능-결과)의 100연결 통과는 지정 요청률·동일 PC·실제 브라우저 5개 표본의 근거다.
200연결 탐색은 pool timeout·미결·보류가 발생한 실패이며 400연결은 NOT_RUN이다. React 제품 화면·이 구조·전체 운영 성능을 검증한 자료가 아니다.
원시 조건·측정 경계·수치는 spike가 원본이며 여기서 새 수용량·성능 보장으로 다시 계산하지 않는다.

한 DB·앱은 배포가 단순하지만 자원 경합·장애점을 공유한다. 한 레인의 직렬 판정 처리량도 앱 수만 늘려 자동 개선되지 않는다.
노드 증설·standby·DB failover에는 진행 권한·old tx fencing·세대·재생·분할 복구와 인증 연결의 별도 설계·검증이 필요하다.
Aggregate 소유권을 서비스 경계로 곧바로 분리하면 교차 tx 계약이 깨지므로 변경안에서 불변식·이행·소비자 영향을 다시 검토한다.

- 설계 초안 단계: 모듈 의존성·필수 tx·단일 원본·계약 예제·미검증 가정을 정적으로 교차 검토한다.
- 구현 단계: ADR-001/002/003의 TM/RC/FA와 공개 생성·교차 Aggregate·두 기기 ACK를 의미 있는 통합 사례로 검증한다.
- 인수·배포 단계: 실제 인증·브라우저·재접속·조회 폭주·장애·배포 환경과 승인 성능 조건을 검증하고 실패·NOT_RUN을 남긴다.

## 10. 사용자 승인 범위와 적용 영향

D-095로 초기 토폴로지·기술 조합, C안 조건부 소유권, 회원×Auction 참여 상태 분리, 공개 확정 시 Auction 생성을 구현 기준으로 채택했다.
운영 시간 정확성·장애 확정권한·성능의 달성은 별도 증거로 판단한다. 미완성 전이·guard 메커니즘과 OPEN은 이번 승인으로 해결된 것으로 기록하지 않는다.
가정이 바뀌면 모듈 공개 API·필수 tx·식별/버전·예제·BE/FE/QA 작업에 미치는 영향을 Contract Owner에게 제시하고 사용자 승인을 기록한다.
구현 에이전트는 채택한 계약·구조 의미를 독자 변경하지 않는다. 인증·입력 범위·권한·재생 기간 등 남은 정책도 임의 생성하지 않는다.
**현재 상태는 D-095의 범위로 ACCEPTED_WITH_OPEN이다. 새 제품 구현·실험·런타임 검증은 모두 NOT_RUN이다.**

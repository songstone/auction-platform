## 2. 해결할 문제와 관측 근거

현재 spike는 트랜잭션 내부에서 읽은 DB 시각으로 준비·재개의 시작과 마감을 저장한다. 레인 gate는 경쟁 변경을 막지만 시각 채취 뒤 커밋까지 흐르는 시간을 제거하지 않는다. 원자료의 재개 10건에서는 기록 시각부터 PostgreSQL 커밋 기록 시각까지 간격과 그 시각 기준 잔여 시간 감소가 확인됐다. 수치·환경·당시 판정은 [SPIKE-001 §6](../../spikes/SPIKE-001.md#기록-시각과-postgresql-커밋-기록-시각--미해결-계약)을 따른다.

측정 경계는 [environment_failures.py](../../../experiments/spike-001/harness/environment_failures.py)의 `committedMs - windowStartMs`와 `deadlineMs - committedMs`다. `committedMs`는 [Engine.events](../../../experiments/spike-001/src/main/java/spike/core/Engine.java)의 `pg_xact_commit_timestamp()`에서 얻는다. **물리 WAL flush 완료·잠금 해제·JDBC COMMIT 반환 뒤의 실제 가용 시간을 직접 측정한 값은 아니다.** 원자료 필드명은 당시 기록으로 보존한다.

따라서 `deadlineAt - effectiveAt = duration`이라는 저장값 산술 검사만으로 실제 전이 경계·접수 가능 구간·복구를 함께 증명할 수 없다. 첫 회차의 공통 시작, 다음 상품 준비, 준비/최초/후속 재개를 모두 다뤄야 한다.

## 3. 구분할 시각과 증거

| 후보 이름 | 의미 / 사용할 수 없는 대체값 |
| --- | --- |
| `receivedAt` | 공식 접수 ADR이 정의할 원요청의 기록 시각. 재개가 실제로 효력을 갖기 시작한 시각을 대신하지 않음 |
| `recordedAt` | 전이 데이터를 트랜잭션 내부에서 기록할 때 관측한 서버 시각. 커밋 완료와 같다고 가정하지 않음 |
| `commitRecordAt` | PostgreSQL 커밋 기록에 담긴 시각. 물리 내구성 완료나 클라이언트 응답 시각과 구분 |
| `commitReturnedAt` | 애플리케이션이 COMMIT 성공 반환을 관측한 시각. 관측 지연이 있고 직후 crash 시 미저장일 수 있음 |
| `effectiveAt` | 승인된 S/N/R에 연결할 권위 전이 확정 시각. 취득·보존·경쟁 접수 처리 방법은 이번 검증의 핵심 |
| `projectedAt` / `publishedAt` | 조회 상태 구성 / 전파 처리 시각. 이미 확정한 전이·개시·마감을 이동시키지 않음 |
| `serverTime` | 응답을 만들 때의 권위 시계 표본 후보. 수신 시점의 정확한 현재 시각이나 입찰 접수 증거가 아님 |

커밋 성공 반환은 설정된 DB 내구성 전제 아래 저장 성공을 확인하는 경계다. 결과 불명은 성공·롤백 어느 쪽으로도 추정하지 않고 원전이 식별자로 확인한다. 서버와 DB 사이의 실제 물리 내구성 완료 순간을 JDBC가 별도 시각 값으로 전달한다고 가정하지 않는다.

## 4. 대안 비교

| 대안 | 해결하는 문제 / 장점 | 남은 문제와 판단 |
| --- | --- | --- |
| A. 현재와 같이 내부 DB 시각을 상태·마감과 한 트랜잭션에 저장 | 구현·복원이 단순하고 상태와 값이 함께 저장됨 | 커밋 지연 중 시간이 소진됨. 이 내부 시각을 승인된 실제 확정 시각으로 해석해도 되는지 기술 근거가 부족하므로 즉시 채택하지 않음 |
| B. 권위 전이 기록과 커밋 증거를 연결하고 조회 상태를 그 기록에서 구성 | 전이 식별·중복·복원 근거와 조회 지연을 분리할 수 있음 | **채택한 구체화 방향**. 커밋 기록 시각도 flush 완료가 아니며 증거 조회·추가 저장 지연이 남음. 정확한 프로토콜과 시간·원자성·접수 연속성은 미완성·미검증 |
| C. COMMIT 성공 후 현재 시각을 읽고 두 번째 트랜잭션으로 시작·마감 저장 | 첫 트랜잭션의 지연을 시각 채취 앞에 둘 수 있음 | 두 번째 커밋 간격과 중간 crash가 다시 생김. 메모리 시각만 사용하거나 단순 재저장하는 방식은 해결책으로 채택하지 않음 |
| D. 미래 활성화 시각을 예약하거나 일정 여유를 더함 | 영속화 시간을 미리 확보할 가능성 | 미래 예약을 실제 재개로 볼 수 있는 근거·지연 상한이 없음. 임의 여유 시간·준비 단계·재개 정책을 추가할 수 있으므로 현 기준선의 해결책으로 채택하지 않음 |

**채택 범위:** B의 최소 프로토콜을 구체화하는 방향을 구현 기준으로 삼는다. 필요한 검증은 구현 중 통합시험이나 격리 실험으로 수행할 수 있다. B가 실패하면 A를 자동 승인하거나 시간을 보정하지 않고 반례와 대체안을 변경 절차로 제출한다. 방향 채택·구현 완료·제품 정책 변경·실행 통과는 서로 다른 상태다.

## 5. B 후보의 최소 프로토콜과 금지되는 지름길

1. 선행 요청과 현재 상태, 중단 발생 건·원명령, 진행 권한을 같은 보호 규약에서 확인한다. 전이마다 재시도에도 유지할 `transitionId`를 갖고 원명령과 연결한다.
2. 전이 종류·원대상·원단계·고정 시간·선행 순번·권한 세대와 원자적 확정 근거를 연결할 권위 전이 기록 후보를 만든다. 중간 기록은 재개 성공 또는 새 정상 진행 상태로 노출하지 않는다.
3. 커밋 증거에서 `effectiveAt`을 결정하는 방법과 원전이의 영속 보존을 검증한다. 원상태·전이·시작·마감을 하나의 권위 있는 변화로 설명할 수 있어야 하며, 시각 값만 먼저 저장하는 부분 성공은 허용하지 않는다.
4. 조회 상태와 outbox는 확정된 원전이에서 구성한다. 읽기 모델이 뒤늦게 갱신되더라도 같은 `transitionId`의 시각을 다시 만들지 않는다. 별도 projection은 미입증 선택 후보로 표시하며 설계 채택과 원자성 입증을 구분한다.
5. 정상 접수가 가능한 동안 접수된 경쟁 요청은 원시각·순번을 보존한다. 전이의 확정 근거가 아직 해석되지 않았다는 이유로 오래된 중단 상태에 근거한 업무 거절을 선기록하지 않는다. 최종 판정은 원전이를 복원한 후 자기 차례에서 한다.
6. 복원된 실제 R 이전 접수는 재개보다 뒤 순번이어도 새 입찰로 승인하지 않는다. R 정각은 공통 순번을 함께 확인한다. 준비 재개는 새 O 이전에 입찰을 승인하지 않는다.
7. 접수·기록의 정상 연속성 또는 원전이 효과를 확인할 수 없으면 [ADR-003](ADR-003-FAILURE-AUTHORITY-AND-RECOVERY.md)의 보류 절차로 연결한다. 메타데이터 조회 실패·단순 응답 유실을 곧바로 모든 경매의 이력 불명으로 확대하지 않는다.

여기서 2→3의 정확한 확정 지점과 3→4 중 지연·장애의 처리가 아직 미완성이다. 특히 **커밋 시각 조회 → projection 저장**만으로는 추가 커밋 간격이 사라지지 않는다. 그 사이 접수를 닫은 채 원시각부터 시간을 소비한다면, 단계 전체 시간과 승인된 접수 가능 구간에 적합하다는 증명을 별도로 해야 한다. 시각을 뒤로 옮기거나 원접수를 재활성화 뒤 시각으로 바꿔 통과시켜서는 안 된다.

내부 상태 이름 후보는 다음과 같다. 이는 새 사용자 결과나 상품 경매 단계를 추가하지 않는다.

| 내부 상태 후보 | 외부 의미 / 복원 규칙 |
| --- | --- |
| `TRANSITION_PENDING` | 원명령 처리 중. 정상 재개 완료로 응답하지 않음. 확정 증거를 찾되 원 R을 추정하지 않음 |
| `TRANSITION_CONFIRMED` | 상태·시각·구간의 일관된 권위 변경과 원기록이 확인된 경우에만 사용 |
| `PROJECTION_PENDING` | 확정 원전이의 조회 구성이 지연됨. 원기록 조회 또는 비최종 안내로 처리하며 시각 재부여 금지 |
| `RECOVERY_REQUIRED` | 확정 효과·접수 연속성 확인이 필요한 내부 분류. 실제 보류 범위와 운영 절차는 ADR-003 원본을 따름 |

## 6. PostgreSQL 시계·내구성의 전제와 한계

- `now()`/`CURRENT_TIMESTAMP`는 트랜잭션 시작 시각이다. gate 대기 뒤 현재 시각을 의도한다면 자동 대체할 수 없다. `clock_timestamp()`는 호출 시각의 벽시계이며 단조 시계가 아니다. [날짜·시간 함수](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT)
- `pg_xact_commit_timestamp()`는 추적 설정 이후 커밋의 정보만 제공하고 vacuum 과정에서 정보가 제거될 수 있다. 따라서 원전이·원판정의 영구 원본으로 단독 사용하지 않는다. [커밋 정보 함수](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-COMMIT-TIMESTAMP)
- `track_commit_timestamp`는 서버 시작 시 설정하며 기본값은 off다. 후보 검증에 사용하면 실행 설정과 재시작·복구 전제를 증거에 남긴다. [설정](https://www.postgresql.org/docs/18/runtime-config-replication.html#GUC-TRACK-COMMIT-TIMESTAMP)
- PostgreSQL 18.0 공식 소스에서 커밋 기록 시각 채취·기록 뒤 WAL flush와 후속 처리가 수행된다. 이 구현 순서로부터 커밋 기록 시각과 내구성 완료·응답 수신 시각을 같게 볼 수 없다고 판단한다. 이는 소스에 근거한 분석이며 실험 버전의 모든 실행 경로를 계측한 결과가 아니다. [고정 소스](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/transam/xact.c#L1348)
- 커밋 타임스탬프가 NULL이 아니라는 사실만으로 해당 원전이의 내구 확정을 증명하지 않는다. 타임스탬프 데이터 기록·조회 경로와 원트랜잭션의 실제 확정 상태를 결합해 확인해야 한다. 동시 조회에서 관측 가능한 범위는 새 실행으로 검증해야 한다. [같은 버전의 조회 구현](https://github.com/postgres/postgres/blob/3d6a828938a5fa0444275d3d2f67b64ec3199eb7/src/backend/access/transam/commit_ts.c)

접수·판정·타이머가 공유하는 영속 시각 연속성 검증을 후보로 둔다. 수신 이력이 없는 경우, 최신 접수보다 큰 값으로 후퇴하는 경우, 재개 직후 후퇴, 개시·마감을 넘는 전진을 다뤄야 한다. 프로세스 단조 시계는 측정 보조이며 재시작 후 원시각이나 다중 프로세스 권위 시각을 대신하지 않는다. 탐지 허용 오차·지연 임계값은 임의로 정하지 않으며, 짧은 단계 시간을 일반 장애 감지 임계값으로 사용하지 않는다.

## 7. API·이벤트 계약에 미치는 영향

| 계약 요소 | 채택 기준선에 연결할 내용 / 미해결 구현 부분 |
| --- | --- |
| 재개 명령 응답 | 접수·처리 중과 실제 재개 성공을 구분. 성공 재전송은 원 `transitionId`·원 R 유지 |
| 상태 조회 | 단계·운영 상태·구간 시작·개시·마감과 그 권위 버전을 함께 반환. 미확정 시각을 정상 단계로 조립하지 않음 |
| 이벤트 | 확정된 같은 변화의 상태·시각 사용. 전송·관측·projection 시각을 `effectiveAt`으로 대체하지 않음 |
| 타임스탬프 표현 | 정의된 wire 표현은 공통 계약 0.1.0의 UtcInstant가 원본. 일정 계산·표시는 Asia/Seoul. 실제 저장·판정 정밀도와 직렬화 일관성은 구현에서 검증 |
| 시각 정밀도 | spike의 밀리초 사용은 제품 정밀도 승인 근거가 아님. 커밋 증거의 정밀도와 경계 비교 손실을 확인해 선택 |
| 클라이언트 카운트다운 | 표시용 추정. 로컬 0초를 최종 결과·입찰 접수·시간 재부여로 처리하지 않음 |

## 8. 추가 검증 계획 — NOT_RUN

모든 사례는 아직 실행하지 않았다. 측정은 HTTP 도착·gate 획득·시각 기록·커밋 기록·COMMIT 반환·권위 전이 확인·조회 구성·공식 접수·최종 판정을 구분한다. 동일 프로세스 구간은 단조 시계도 기록하고 서로 다른 시계의 매핑 오차를 밝힌다. 관측 도구가 제공하지 않는 물리 flush 완료 순간은 측정값으로 발명하지 않는다. 커밋 전후 시각으로 만든 범위도 불확실성을 나타낼 뿐 중간값·후시각을 실제 R로 대입하는 근거가 아니다.

| ID | 주입·시나리오 | 승인 정책에 따른 기대 결과 / 확보할 증거 |
| --- | --- | --- |
| TM-01 | 첫 회차 시작·다음 준비·세 단계 재개에 저장 지연 주입 | 하나의 S 또는 해당 N/R과 상태·구간·고정 전체 시간이 일치. 지연이 단계보다 짧거나 길 때 실제 경계·접수 가능성과 보류 판단까지 검사 |
| TM-02 | 원전이 커밋 후 증거 조회·projection 저장을 각각 지연 | 새 시각 재부여·과거 상태 선거절 없음. 공식 접수 원시각·순번과 복원한 전이로 판정. 전체 시간 주장 실패 시 후보 실패로 기록 |
| TM-03 | 전이 기록 전후·커밋 결과 불명·projection 전후 강제 종료 | 저장된 원전이 한 번 복원 또는 이력 확인 필요 상태 유지. 원 R을 재생성하거나 부분 성공을 노출하지 않음 |
| TM-04 | 재개 접수 뒤 실제 R 이전·정각·이후 입찰과 순번 양방향 | 재개 전 입찰은 뒤 순번이어도 거절. 정각은 유효 재개 뒤 순번과 다른 조건 확인. 준비 재개는 O까지 입찰 불가 |
| TM-05 | 정상 개시·마감 callback 지연과 옛 timer 재실행 | 유효 O·현재 마감 유지. 선행 요청을 반영하며 callback 실행 시각으로 시간을 갱신하지 않음 |
| TM-06 | 시계 후퇴·전진, 접수 이력 없음·재개 직후·재시작 | 탐지한 사실과 판별 불명 구간 기록. 근거 없는 정상 전이·오낙찰 금지. 탐지 못한 범위도 결과로 보고 |
| TM-07 | 커밋 메타데이터 미설정·조회 불가·정리·DB 복원 | 원전이 보존 경로 확인. 메타데이터가 없으면 원 R을 현재 시각으로 추정하지 않음 |
| TM-08 | 재개 응답 유실 후 원명령 재전송, 그 사이 새 중단 | 원결과·원 R 반환, 새 중단 유지. 신규 재개 효과·시간 재부여 없음 |

기술 담당은 각 시나리오의 주입 위치·계측 방법·반복 수·실행 환경을 제안하고, QA는 승인된 정책에서 기대값을 독립적으로 도출한다. 환경·반복 수·실험 계획이 정해지지 않았다는 이유로 이번 표를 실행 통과로 표기하지 않는다.

## 9. 채택 범위와 병렬 작업 조건

D-095로 권위 전이 기록·시간 의미·B 구체화 방향을 채택했다. 시스템 설계 1.0과 정의된 API·이벤트 계약 0.1.0을 구현 기준선으로 사용하며, 남은 OPEN과 B의 미완성·미검증 상태를 유지한다. 정의된 wire 표현의 원본은 공통 계약이고 실제 S/N/R 취득·내구성·접수 가능 구간의 성공을 이번 승인으로 확정하지 않는다.

단계 전체 시간의 실제 충족·운영 적용 적합성·보장을 판단하려면 다음 근거가 필요하다. 이는 이번 채택의 효력을 추가 실험 뒤로 미루는 조건이 아니라 구현·운영 보장을 확인할 책임이다.

1. 실제 S/N/R 확정 위치와 시각의 영속 원본, 그 위치가 승인 정책을 만족한다는 설명.
2. 전체 단계 시간·재개 하한·경쟁 접수·중복 재개·정상 지연·장애를 한 이력으로 설명하는 실행 증거.
3. COMMIT 반환·메타데이터 조회·projection 지연과 그 사이 접수의 처리, 데이터 복구 후 같은 경계 복원 근거.
4. 정밀도·시계 연속성·내구성 전제와 보장하지 못한 범위. 정책 변경이 필요해지면 별도 변경안으로 제시.

BE·FE·QA는 채택된 버전의 시간 의미·재개 응답과 승인 도메인 규칙을 기준으로 병렬 작업할 수 있다. 실제 경계 기반 인수 통과·보장 주장은 실행 증거로 별도 판단한다. B의 정확한 확정 지점·추가 commit 간격·접수 가능 구간은 운영 적용 전에 해결해야 할 중요한 미해결 위험이며, TM의 새 실행 상태는 NOT_RUN이다.

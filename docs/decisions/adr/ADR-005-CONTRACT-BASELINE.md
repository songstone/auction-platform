# ADR-005 — 공통 계약의 원본·버전·변경 권한

| 항목 | 값 |
| --- | --- |
| 상태 | **ACCEPTED_WITH_OPEN — 정의된 계약·공식 원본·버전/변경 절차 채택. 남은 OPEN·미검증 위험 유지** |
| 작성일 / 책임 | 2026-10-15 / Solution Architect & Contract Owner |
| 채택 승인 | 2026-10-15 / D-095. 현재 시스템 설계·정의된 API·이벤트를 구현 기준선으로 승인 |
| 계약 기준선 | `0.1.0` — 출발 검토본 `0.1.0-draft.2` |
| 시스템 기준선 | SYSTEM-DESIGN `1.0` — 출발 검토본 `0.2` |
| 범위 | HTTP/이벤트 계약의 단일 원본, 소비자 병렬 작업, 변경·검토·사용자 승인 기준선 |
| 새 실행 | 계약 문서 작성. 제품 구현·기능·동시성·장애·브라우저·성능·배포 모두 **NOT_RUN** |

## 1. 해결할 문제

BE·FE·QA가 서로의 구현을 기다리지 않고 같은 요청·원판정·공개 상태·재생 의미를 사용할 원본이 필요하다. 구현별 DTO·오류·재시도를 따로 정하면 같은 입찰이 성공/실패·미확인 해제·재개로 다르게 해석될 수 있다.

작성 단계에는 사용자 승인 전까지 초안을 유지했다. 이후 D-095로 남은 OPEN·미검증 위험을 유지한 현재 시스템 설계와 정의된 API·이벤트를 구현 기준선으로 채택했다. 설계·계약 채택, 실행 PASS, 운영 보장은 서로 다른 상태이며 이번 승인에 제품 구현·새 실험 성공을 포함하지 않는다.

## 2. 채택한 원본 분리

| 원본 | 이 원본만 소유할 내용 |
| --- | --- |
| [openapi.yaml](../../../contracts/openapi.yaml) | HTTP 경로·메서드·인증/권한·입출력·오류·모든 JSON 스키마와 예제. SSE payload도 같은 components 사용 |
| [auction-events.md](../../../contracts/auction-events.md) | SSE 프레임·이벤트 의미·버전/순서·중복·커서·재생·snapshot/실시간 인계 규약 |
| [contracts/README](../../../contracts/README.md) | 원본 탐색·범위/OPEN 지도·독립 작업/검사 상태. 필드·오류 스키마의 별도 정본 아님 |
| 이 ADR | 버전·검토/승인 상태·Contract Owner 책임·변경 절차·호환성 판단 |

[SYSTEM-DESIGN](../../architecture/SYSTEM-DESIGN.md)은 모듈·트랜잭션·배포 구조를, 기존 ADR-001~004는 시간·접수·장애·구조 선택 이유를 소유한다. 제품 R/AC·D/OPEN·도메인 INV는 기존 원본을 유지한다. 새 스키마를 ADR이나 FE/BE 문서에 복제해 독립 수정하지 않는다.

## 3. 표현 선택과 대안

OpenAPI 3.1.1을 사용해 기계 검증·mock·소비자 타입 생성에 공통 입력을 제공하는 방식을 채택했다. Schema Object의 JSON Schema 2020-12 기반 의미를 사용하되 validator·generator 호환성은 도구 선정 시 확인한다. [OpenAPI Schema Object](https://spec.openapis.org/oas/v3.1.1.html#schema-object), [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core)

SSE는 스트림 복원·watermark·live 인계 의미가 일반 HTTP JSON 응답만으로 충분히 설명되지 않아 별도 의미 문서로 둔다. payload 필드는 OpenAPI 참조로 한 번만 정의한다. HTTP 명세와 독립 AsyncAPI 원본을 추가하는 선택은 현재 추천하지 않는다. 두 JSON 정본을 동기화할 비용과 이득을 아직 비교하지 않았다.

대안인 Markdown만의 계약은 도입이 작지만 필드·필수값·분기·예제의 기계 검사와 소비자 동기화가 어렵다. 구현 코드로부터만 계약을 추출하면 다른 담당이 서버 완료를 기다리고 구현 우연을 정책으로 채택하기 쉽다. 계약을 먼저 관리하고 구현이 승인 기준선에 맞는지 확인하는 방향을 채택했다.

wire 선택은 OpenAPI가 원본이다. 문자열 금액/카운터·opaque ID·UTC 시각 프로파일·쿠키/CSRF·접수/판정/ACK 분리의 이유와 미결정 범위는 README에서 탐색한다. 시각 문자열 정밀도가 실제 시계·commit·접수 보장을 뜻하지 않으며, HTTP `202`의 서비스 내구 접수 조건도 표준 자체의 보장이 아니다. [RFC 3339](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6), [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

## 4. 상태·버전·승인 기준선

| 계약 검토 상태 | 의미 / 다음 조건 |
| --- | --- |
| `DRAFT` | 미승인 후보. 미결정 정책·기술 가정·미실행을 명시하며 mock/소비자 검토 가능 |
| `REVIEWED` | BE·FE·QA의 문서 검토와 관련 정적 검사 범위·잔여 사항을 기록. 사용자 승인이나 실제 실행 PASS가 아님 |
| `USER_APPROVED` | 사용자가 승인한 버전·파일 목록·적용 범위·OPEN/가정·검증 상태·Git commit 또는 hash를 명시한 계약 기준선 |

초기 작성본은 `0.1.0-draft.1`이었고 D-092~D-094 동기화본은 `0.1.0-draft.2`였다. D-095의 채택 계약 버전은 `0.1.0`이다. OpenAPI 문법 버전, HTTP 경로의 `/api/v1`, 이벤트 `schemaVersion`, 영속 stream 세대·상태 버전은 서로 다른 식별이며 하나를 올려 나머지 의미를 자동 변경하지 않는다.

`0.1.0-draft.2`에서 `SessionUser.roles`의 동시 운영/회원 역할을 금지한 것은 D-092~D-094의 제품 정책 반영 이력이다. 당시 제품 정책 승인만으로 ADR·계약을 승인하지 않았고, 현재 채택은 별도의 D-095가 근거다. 이번 `0.1.0` 전환은 정의된 계약의 승인 상태 변경이며 이벤트 payload 구조·순서 의미를 바꾸지 않아 `schemaVersion` 1을 유지한다.

초안 변경도 새 draft 식별과 diff로 추적한다. 사용자 승인 뒤 breaking change는 계약 major 버전과 이행/폐기 계획을 제시하는 것을 원칙으로 한다. `0.x`라는 이유로 승인된 소비자를 임의로 깨지 않는다. URL·이벤트 버전을 함께 바꿀지는 실제 소비자와 이행안을 보고 결정한다.

D-095는 정의된 operation·필드·오류·이벤트 의미를 구현 기준선으로 채택하되 남은 OPEN·deferred·미검증 위험은 유지하는 범위 승인이다. 미정 정책 값·정의되지 않은 표면까지 확정한 것으로 확대하지 않는다. 이후에도 단순 작성 지시·검토 완료·실험 실행 승인을 계약 변경 승인으로 바꾸지 않는다.

## 5. 변경 절차와 구현 담당의 권한

1. 구현 담당은 공유 계약을 임의 변경하지 않는다. 필요한 변화·관련 R/D/INV·원본 diff·입출력 예제·호환성·BE/FE/QA 영향을 Contract Owner에게 제출한다.
2. Contract Owner는 정책 변화와 기술 표현 변화를 구분한다. 해결된 제품 정책을 다시 OPEN으로 돌리지 않고, 새 정책 결정이 필요하면 미정으로 남겨 사용자에게 결정 근거를 제시한다.
3. 원본 하나에서 수정하고 연결 문서는 참조를 맞춘다. 구현 내부 예외를 새 HTTP 코드·enum·이벤트로 먼저 공개하거나 소비자가 묵인하도록 우회하지 않는다.
4. BE·FE·QA가 변경 예제·권한·원접수/판정/ACK·중복·복원·재접속을 독립 검토한다. 영향을 받는 소비자·mock·생성물과 필요한 이행 검증을 지정한다.
5. 사용자에게 구체 diff와 적용 범위·남은 OPEN·가정·검사/실행 상태를 제시한다. 승인된 범위만 기준선으로 기록하고 구현·소비자를 같은 버전으로 맞춘다.
6. 실행 검증은 변경 경로에 맞게 수행한다. 구조 검사 결과를 업무 정합성·시간·장애·성능 보장으로 표시하지 않는다.

CODEOWNERS·보호 브랜치·필수 CI·계약 호환성 diff는 절차를 기술적으로 강제할 후보이며 현재 설정 완료가 아니다. 도구가 없다는 이유로 구현 담당에게 의미 변경 권한이 생기지 않으며, 도구를 제안했다는 이유로 무단 변경이 이미 차단됐다고 보고하지 않는다.

## 6. 호환성 판단의 최소 기준

| 변경 | 판단 후보 |
| --- | --- |
| 경로/메서드·필수 요청/응답 필드·자료형·금액/시각 표현 변경 | breaking change로 평가하고 소비자 이행을 제시 |
| 기존 필드 제거·필수화·허용값 축소·null/생략 의미 변경 | 기존 소비자의 요청·응답과 분기를 깨는지 확인. 독자 적용 금지 |
| enum 추가·오류/업무 거절 의미 변경 | 닫힌 enum 소비자를 깰 수 있음. 추가라는 이유만으로 호환이라고 판단하지 않음 |
| 접수 시각·순번·원판정/ACK·보류·재생/커서 의미 변경 | 필드가 같아도 의미상 breaking change로 평가 |
| 선택 필드·새 operation·새 이벤트 추가 | 기존 strict 스키마·미지 이벤트 처리·권한/부하 영향까지 확인한 뒤에만 호환 추가로 분류 |
| 오탈자·설명 보완 | 실제 검증값·권한·상태 해석을 바꾸지 않는지 확인한 뒤 patch 후보로 분류 |

정확한 버전 숫자만으로 호환성을 증명하지 않는다. 서비스와 이벤트 소비자가 승인된 기준선의 의미를 함께 이해하는지 예제와 변경 영향으로 검토한다. `Last-Event-ID` 같은 전송 기능의 존재가 서비스 replay 계약을 자동 보장하지 않는다. [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header)

## 7. 병렬 작업·검증·남은 제약

BE는 계약의 저장·명령 경계를 구현하고 FE는 같은 버전의 mock/예제로 화면 상태와 복구를 만들며 QA는 승인 AC/INV/TS에서 기대값을 독립 도출한다. 아직 모르는 정책 값을 구현자가 채워 넣지 않도록 OpenAPI의 문서용 `x-open-decisions`·`x-draft-status`·`x-deferred-surfaces`와 연결하고, 실제 실행 증거는 `x-verification-status`로 별도 표시한다.

BE·FE·QA는 채택 계약 0.1.0의 정의된 범위를 같은 버전으로 소비한다. 계정/입력/조회 정책이 미정인 표면까지 전체 프로덕션 독립 구현 가능으로 선언하지 않고 잔여 OPEN을 구분한다. 전체 성능·장애 실험 통과를 이번 채택의 일괄 선행조건으로 두지 않으며 검증하지 않은 보장은 계속 미검증이다.

수동 정적 검사기와 결과 보고서를 제공했다. 실제 검사 범위·실행 방법·도구 버전은 [contracts/README](../../../contracts/README.md#6-검증-기록)와 연결 보고서가 원본이다. 스키마의 `format`과 서비스 업무 규칙의 실제 검증 여부는 별개다. 생성 SDK·mock·실제 HTTP/SSE·DB·다중 기기·장애·브라우저는 별도 실행 증거가 필요하다.

| 현재 검증 | 상태 |
| --- | --- |
| OpenAPI 수동 정적 검사·계약 간 독립 문서 검토 | **CONTRACT_STATIC_ONLY / PASS**, 문서 검토 PASS. 실제 수행 범위와 결과는 contracts/README가 기록 |
| 제품 구현·기능·동시성·장애·브라우저·성능·배포 | NOT_RUN |

**현재 결론:** D-095로 원본 분리·변경 절차와 정의된 계약 0.1.0을 구현 기준선으로 채택했다. 남은 OPEN·미검증 위험은 유지하며 정적 검사 통과나 이번 채택은 실제 운영 보장을 대신하지 않는다.

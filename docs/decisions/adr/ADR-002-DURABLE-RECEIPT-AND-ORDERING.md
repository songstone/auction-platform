## 1. 문제와 기준선

[DOMAIN-MODEL](../../architecture/DOMAIN-MODEL.md) §5.2·§6과 [결정 기록](../DECISION-LOG.md)의 승인 정책을 실제 저장·복구 계약으로 연결한다.
요구사항의 정본은 [MVP PRD](../../product/MVP-PRD.md), 업무 설명은 [경매 규칙](../../product/AUCTION-RULES.md)이며 이 ADR에서 제품 정책을 복제·변경하지 않는다.
공식 접수는 인증·기본 형식 확인 후 공식 기록에 넣는 사건이며 입찰 승인과 다르다(D-055).
같은 회차·레인의 진행에 영향을 주는 외부 요청은 공통 증가 순번으로 판단한다(D-063).
후속 마감의 기준은 원공식 접수 시각이며 판정·응답·화면 표시 시각이 아니다(D-057).

[SPIKE-001](../../spikes/SPIKE-001.md) §2·§4는 PostgreSQL 레인 gate, 롤백 가능한 행 counter, 접수/판정 분리의 지정 사례를 실행했다.
그러나 단일 회차 fixture이며 Round 순서·제품 인증·복원 세대·운영 전체 정확성의 증거는 아니다.
접수 시각과 commit 사이에도 간격이 있다. 이 문서는 원시각을 commit 시각으로 바꾸거나 두 시각이 같다고 주장하지 않는다.
전이 시각의 의미·정밀도·commit 간격 처리는 [ADR-001](ADR-001-TRANSITION-TIME.md)을 따른다.
장애 진행 권한·보류 범위·복구 증거·재개 자격은 [ADR-003](ADR-003-FAILURE-AUTHORITY-AND-RECOVERY.md)을 따른다.

## 2. 채택안과 대안

**채택: 같은 PostgreSQL 자원에서 짧은 접수 트랜잭션과 별도 순서 판정 트랜잭션을 운용한다.**
레인 gate는 `(roundId, laneId)` 행의 `FOR UPDATE` 후보이며 모든 접수·판정·자동 전이가 같은 보호 규약에 참여한다.
Java 메모리 큐·락이나 특정 JVM만을 권위 있는 순서·복구 근거로 사용하지 않는다.

| 후보 | 해결하는 문제·이유 | 비용·미검증 경계 | 판단 |
| --- | --- | --- | --- |
| 내구 접수 후 별도 판정 | 접수 증거·미결 순서를 먼저 보존하고 응답 유실·재시작에도 원접수로 판정 | 두 commit, gate/pool 대기, 원판정 조회·적체 관리 필요 | 채택, 미검증 위험 유지 |
| 접수와 판정을 한 트랜잭션으로 합침 | DB 왕복·중간 상태를 줄일 수 있음 | 판정 지연이 접수 유지 비용에 섞임. 장애 시 접수 사실의 복구 의미를 다시 검증해야 함 | 비교 미실행 |
| 낙관적 충돌 검사와 재시도 | 배타 구간 축소 가능성을 검토 | 재시도에도 원접수·선행 순서·자동 경계를 보존해야 함 | SPIKE 비교 NOT_RUN |
| 메모리 큐 또는 외부 브로커를 접수 정본으로 사용 | 별도 처리·확장 경계 제공 가능 | DB 효과와 중복 기록의 이중 기록·복구 계약이 추가됨 | MVP 우선 채택 제안 아님 |

한 레인의 직렬 구간은 서버 증설만으로 사라지지 않는다. 다른 레인에 전역 입찰 순서를 추가하지 않는다.
행 잠금은 트랜잭션 동안 같은 행의 경쟁 변경을 막지만 HTTP 요청의 도착 공정성을 보장하지 않는다.
근거: [PostgreSQL 18 행 잠금](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS).

## 3. 식별자와 순서의 의미

| 후보 필드·키 | 의미·범위 | 혼용 금지 |
| --- | --- | --- |
| `roundId + laneId` | 해당 회차 레인 접수·판정 스트림 식별 | 재사용된 레인 번호만으로 식별 불가 |
| `memberId + requestId` | 입찰 의도·원요청의 중복 식별. 최초 `auctionId + submittedAmount`에 결합 | 회차·현재 화면·세대가 달라져도 같은 키를 새 입찰로 재사용 불가 |
| `operatorId + commandId` | 종류·원대상·사유 등 원명령 내용에 결합 | 재전송을 새 명령으로 해석 불가 |
| `suspensionOccurrenceId` | 재개가 해제하려는 중단 발생 건. 회차·레인과 함께 검증 | 같은 상품이라는 이유로 새 중단에 옛 재개 적용 불가 |
| `receiptSequence` | 해당 회차·레인에 내구 접수된 외부 요청의 공통 증가 순번 | 입찰 번호·DB 저장 ID·공개 이벤트 버전과 다름 |
| `laneVersion` | 해당 공개 레인 상태 스트림의 revision 후보 | 거절·개인 요청 처리마다 반드시 증가하는 접수 순번이 아님 |
| `streamEpoch` | 회차/복원으로 cursor 의미가 바뀌는 세대를 구별할 불투명 식별자 후보 | ADR-003의 장애 진행 권한 세대와 의미를 합치지 않음 |
| `eventId` | outbox 항목의 고유 식별 후보 | 전역 ID 증가를 commit·전역 재생 순서로 사용 불가 |

입찰·상품 취소는 원상품 경매를 대상으로 유지한다. 레인 중단·재개는 회차·레인을 대상으로 한다(D-066).
Auction의 소속 레인은 서버 기록으로 결정하며 클라이언트가 다른 레인에 보내 접수 순서를 바꾸게 하지 않는다.
정의된 키·정수의 wire 표현과 `streamEpoch` 의미는 공통 계약 0.1.0이 원본이다. 키 생성·운영 길이 제한과 세대 생성/교체의 실제 구현은 남은 OPEN·검증 대상으로 구분한다.
복원 후 세대 변경은 잃어버린 원판정을 복구하지 않는다. 키 이력 소실은 새 효과 실행 허가가 아니며 ADR-003의 불명 판정을 따른다.

## 4. 인증·기본 형식과 업무 판정

| 구간 | 확인할 내용 | 응답의 의미 |
| --- | --- | --- |
| 접수 전 | 인증, 회원/운영자 역할 권한, 필수 필드·타입·식별자 형식, 승인된 금액 기본 입력 조건 | 실패는 프로토콜/보안 오류. 원입찰의 최종 거절로 기록하지 않음 |
| 접수 전 프로토콜 | 동일 키 원내용, 공유 의도 등록 확인·원경매/금액 연결, 원대상 라우팅 | 중복은 기존 처리로 연결. 충돌은 원요청을 보존하며 새 공식 순번 없음 |
| 공식 순번의 판정 | 자기 상품·최고입찰자 여부, 현재 금액·단계·개시/재개 하한·현재 마감, 제어 명령 업무 자격 | 원최종 승인 또는 거절을 내구 기록 |

가격·시간·문자·사진의 미승인 범위를 기본 형식이라는 이름으로 추가하지 않는다(OPEN-05).
등록·접수 전에 오래된 현재가·마감으로 업무 거절하거나 금액을 자동 보정하지 않는다.
중단 중에도 기본 조건을 통과한 요청의 접수·거절 기록과 유효 입찰 승인 중단을 구분한다.
인증·저장·통신 오류, 공유 등록 실패, 내용 충돌은 원입찰 최종 거절이나 제한 해제를 뜻하지 않는다.
접수 전 오류의 HTTP 상태·오류 코드와 공식 업무 거절 코드의 네임스페이스는 계약에서 분리한다.

## 5. 접수 트랜잭션 후보

1. 인증·형식 확인 뒤 기존 키를 확인한다. 원기록이 있으면 원내용 비교 후 원접수/원결과를 반환한다.
2. ADR-003의 상태 변경 권한을 검증하고 해당 회차·레인 gate를 획득한다. 획득 뒤 원키와 프로토콜 조건을 재확인한다.
3. gate 이후 DB 시각을 한 번 채취해 `receivedAt` 원값을 만들고 레인 행 counter를 증가시킨다.
4. 원키·원내용·대상·원시각·순번·미결 상태를 같은 트랜잭션에 저장하고 내구 commit한다.
5. commit 성공을 확인한 뒤에만 공식 접수 확인을 응답한다. 아직 판정하지 않았다면 처리 중으로 표현한다.

`receivedAt`은 3번의 기록 시각이며 4번은 그 접수 사실을 확정하는 저장 경계라는 후보다.
pool/gate 대기 이전 HTTP 수신 시각이나 클라이언트 시각으로 소급하지 않는다.
HTTP가 마감 전에 도착했어도 gate 이후 원시각이 마감 뒤라면 늦은 접수로 판정될 수 있다.
counter·원요청은 함께 롤백된다. 롤백된 임시 순번·원시각을 접수 증거로 외부에 발표하지 않는다.
원요청·counter의 같은 트랜잭션 저장은 [PostgreSQL 18 트랜잭션](https://www.postgresql.org/docs/18/tutorial-transactions.html)의 원자성을 사용하는 후보이며 실제 원자성 경로는 RC-03/04에서 검증한다.
제품이 gapless 순번을 요구하는 것은 아니다. 처리기는 실제 내구 미결 기록을 읽고 저장 일관성을 확인하며 숫자 구멍만으로 다음 요청을 영구 대기시키지 않는다.

`clock_timestamp()`는 호출 시점 시각이고 `CURRENT_TIMESTAMP`는 트랜잭션 시작 시각이므로 대기 후 채취 목적에는 전자를 비교한다.
이는 단조 시계 보장이 아니다. 역행·시간 증거 불명은 임의 clamp·자동 거절 대신 ADR-001/003에 연결한다.
근거: [PostgreSQL 18 현재 시각 함수](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT).
행 counter를 권하는 이유는 요청과 같은 트랜잭션으로 취소하기 위해서다. `nextval`은 abort 시 회수되지 않는다.
근거: [PostgreSQL 18 sequence](https://www.postgresql.org/docs/18/functions-sequence.html).

내구 성공의 후보 전제는 `fsync=on`, 중요 트랜잭션의 `synchronous_commit=on`, 실제 저장 장치/배포 설정 확인이다.
로컬 WAL flush의 의미를 원격 복제·failover·전원/디스크 손실까지 보장한 것으로 확대하지 않는다.
근거: [PostgreSQL 18 WAL 설정](https://www.postgresql.org/docs/18/runtime-config-wal.html#GUC-SYNCHRONOUS-COMMIT).
계측용 `pg_xact_commit_timestamp`는 PostgreSQL의 commit 기록 시각이며 WAL flush 완료나 JDBC `commit()` 성공 응답 수신 시각을 대신하지 않는다.
SPIKE의 recorded→commit timestamp 간격을 물리 내구 완료의 직접 실측으로 사용하지 않는다. 해당 함수는 활성화·보존 제약이 있으므로 원접수/원판정의 영구 정본도 아니다.
근거: [PostgreSQL 18 commit 정보 함수](https://www.postgresql.org/docs/18/functions-info.html#FUNCTIONS-COMMIT-TIMESTAMP), 전이 경계 비교의 정본은 ADR-001이다.

## 6. 판정 트랜잭션과 자동 경계

판정자는 같은 권한·gate 규약 아래 해당 회차·레인의 가장 낮은 내구 미결 순번을 선택한다.
여러 worker가 있어도 앞선 미결을 건너뛰어 후행 요청을 판단하지 않는다. `SKIP LOCKED`로 같은 레인의 순서를 바꾸지 않는다.
원공식 접수 시각과 선행 효과로 현재 개시·마감·중단 상태를 재구성하고 승인된 경계 규칙을 적용한다.
입찰의 승인 효과, Bid·최고입찰·단계·마감, 원최종 판정, 필요한 공개 버전·outbox를 같은 commit에 보존한다.
거절도 원최종 판정을 보존하되 가격·마감은 바꾸지 않는다. 공개 상태 변화가 없으면 공개 버전 증가를 강제하지 않는다.
개인 원판정 저장·조회와 공개 상태 outbox의 대상·권한을 구분하며 공개 payload에 회원 키·비공개 금액을 넣지 않는다. 개인 실시간 알림의 추가 채택은 이 ADR의 결정 범위가 아니다.

자동 개시/마감은 외부 접수 순번을 타이머 호출 순서로 대체하는 요청이 아니다.
gate 안에서 선행 접수와 현재 유효 경계를 확인하여 개시 정각·정상 마감 정각의 승인된 우선을 적용한다.
접수 commit 전 틈은 같은 gate가 타이머의 추월을 막아야 한다. 판정 commit이 늦어도 원접수 시각을 이동시키지 않는다.
장기 지연·이미 지난 새 마감·불명 기록의 처리와 실제 전이 시간은 ADR-001/003에 위임한다.
outbox 전송은 commit 뒤 수행한다. 네트워크 송신·클라이언트 ACK를 DB 입찰 트랜잭션 안에서 기다리지 않는다.
outbox 소비·SSE 전달은 중복 가능성을 전제하며 같은 DB 효과를 한 번으로 만드는 중복 보장과 구분한다.
원판정 저장 후 응답/전파 실패는 입찰을 되돌리지 않고 원키 조회·전파 재생으로 복원한다.

## 7. 공유 의도·실제 접수·원최종 판정 ACK

| 단계 | 내구 사실·허용 동작 | 금지할 추론 |
| --- | --- | --- |
| 공유 의도 등록 | 회원×Auction당 동시 미확인 의도 하나, 회원+키와 원경매·금액 고정 | 등록 시각을 접수 시각·순번 예약으로 사용 |
| 등록 확인 | 어느 기기든 동일 의도 조회·인계. 등록 확인 뒤 같은 내용의 실제 입찰 제출 | 등록 timeout을 의도 폐기·새 키 허용으로 해석 |
| 실제 접수 | §5에서 처음 공식 접수된 시각·순번 확보. 동시 동일 키는 하나의 원기록 | 재전송마다 새 시각·순번·가격 효과 생성 |
| 최종 판정 확인 | APPROVED/REJECTED 후보 상태와 원요청의 불변 판정 식별을 앱에 전달 | 현재 최고자·낙찰자·최신 snapshot을 원승인과 동일시 |
| 앱 자동 ACK | 인증된 어느 기기든 원키·원판정 식별에 결합하여 수신·반영 사실 확인 | 서버 전송·SSE 수신만으로 ACK 완료 간주 |

ACK와 해당 공유 제한 해제는 같은 트랜잭션으로 보호하고, 중복 ACK는 같은 결과로 처리한다.
ACK 유실 시 같은 ACK를 재전송한다. 늦은 옛 ACK는 원의도에만 적용하며 새 의도를 해제하지 않는다.
원최종 판정이 없는 ACK는 제한을 해제하지 않는다. 모든 기기 ACK·수동 열람 버튼을 요구하지 않는다.
MVP 원판정·중복 식별 기록에는 자동 TTL을 두지 않는다. 운영 보존·삭제는 OPEN-12의 별도 결정이다.

## 8. 실패·불명과 동일 키 복구

| 관찰 | 서버·클라이언트의 후보 처리 | 확정하면 안 되는 결론 |
| --- | --- | --- |
| 접수 전 인증/형식 실패 | 해당 시도의 프로토콜 오류. 필요 조건 수정 뒤 기존 의도·키 상태 확인 | 원입찰이 최종 거절됨 |
| 접수 트랜잭션 rollback 확인 | 공식 접수 효과 없음. 같은 키 재제출의 첫 내구 접수에 새 실제 시각·순번 부여 | 이전 HTTP 도착 시각에 접수됨 |
| commit 호출 뒤 연결 유실·결과 불명 | 접수 여부 미확인. 권위 DB에서 원키 조회·동일 키 재제출로 진행 중/원기록과 합류 | 미접수 또는 실패 확정, 새 키 교체 |
| 단순 조회 `NOT_FOUND` | 해당 조회에서 원기록을 찾지 못함. 같은 의도·키로 복구를 이어감 | 영구 미접수·최종 거절·제한 해제 |
| 원접수만 존재 | 원순번 대기/판정 또는 완전 이력 복구. 원접수 보존 | 지금 상태로 재접수 시각 갱신 |
| 원최종 판정 존재 | 원승인/원거절을 반환하고 ACK 복구 | 지금 금액·새 재개 하한으로 재심사 |
| 판정 commit 결과 불명 | 원판정·효과를 함께 확인. 원자성 증거가 불명하면 ADR-003 보류 | 효과 없는 거절을 새로 만들어 덮기 |
| HTTP/조회 timeout·재시도 소진 | 처리 확인 중 유지, 동일 키 조회/재전송 재개 가능 | timeout을 제3의 최종 결과로 저장 |

불명 commit의 재제출은 원키 고유 제약과 같은 gate 아래 기존 미완료 트랜잭션과 경쟁을 해결한 뒤 판단해야 한다.
낡은 replica·캐시·장기 snapshot의 부재만으로 새 접수를 만들지 않는다. 권위 조회의 일관성·연결 복구 절차를 검증해야 한다.
내용 충돌은 원기록을 유지하며 원요청 최종 거절을 대신하지 않는다. 충돌 복구용 새 키 자동 생성도 하지 않는다.
완전 이력과 원효과가 불명인 장애 복구를 개인 조회의 `NOT_FOUND`와 구분한다. 후자는 경매 전체 보류의 충분조건이 아니다.
운영 명령도 동일 키 원결과를 반환한다. 재개 재전송은 원 R을 유지하며 새 중단 발생 건을 해제하지 않는다.

## 9. Round 범위와 계약 영향

레인 gate만으로 제품 전체의 순서·원자성을 해결했다고 판단하지 않는다.
모집·공개 전 출품 접수/수정/레인 수 변경, 최소 대기 수 배정·공개 고정은 Round 범위 순서와 보호 규약이 필요하다(D-081, D-087~090).
자동 회차 시작과 회차 취소는 Round 공통 판정 순서, 단일 진행 회차 점유, 공통 실제 시작을 함께 보호해야 한다(D-084, D-067).
서로 다른 scope의 순번을 직접 비교하지 않는다. cross-scope 명령의 잠금 순서·위임·부분 실패 복구는 후속 SYSTEM-DESIGN에서 별도 명세한다.

채택한 OpenAPI는 등록 상태·공식 접수/처리 상태·원최종 판정·ACK 상태를 분리한다. 접수 확인을 입찰 승인으로 명명하지 않는다.
이벤트 계약은 `(streamEpoch, roundId, laneId, laneVersion)` 범위의 중복/순서와 snapshot 재동기화를 정의한다.
세대 불일치 때 옛 cursor로 수치 비교를 계속하지 않고 snapshot 및 본인 미확인 요청을 다시 확인한다. 구체 재생 보존 범위는 후속 승인 대상이다.
정의된 API 경로·enum·HTTP 코드·event schema는 공통 계약 0.1.0이 원본이다. 미정 재시도 간격/횟수·보존 등은 이번 채택으로 임의 확정하지 않는다.

## 10. 증거와 후속 실험

아래 RC는 이 ADR의 고유 검증 ID다. 기존 증거 열은 SPIKE 보고서의 제한된 관찰이며 **새 후보 검증은 전부 NOT_RUN**이다.

| ID | 검증할 반례·조건 | 기존 증거 / 새 완료 조건 |
| --- | --- | --- |
| RC-01 | 같은 금액 경쟁·같은 기록 시각·선행 무효 요청 | SPIKE §4 지정 사례. 실제 인증·round namespace에서도 원순번 첫 유효만 승인 |
| RC-02 | gate/pool 대기 전후 마감 통과·HTTP 도착 역전 | SPIKE §2의 접수 위치. HTTP 순서 약속 없이 gate 이후 원시각·순번 일치 검증 |
| RC-03 | counter 증가·원요청 insert 뒤 rollback/프로세스 종료 | SPIKE §6 commit 전/후 종료 사례. 새 저장 구조에서 미commit 순번 외부 노출 없음 검증 |
| RC-04 | 접수/판정 commit 응답 유실·동일 키 동시 재제출 | SPIKE 중복·종료 사례. 실제 네트워크 commit 불명에서 원기록 합류·효과 한 번 검증 |
| RC-05 | 개시/마감 정각·접수 commit 틈·늦은 타이머 | SPIKE §4 합성 경계. ADR-001 후보와 실제 시각·commit 간격을 함께 검증 |
| RC-06 | 공유 등록 동시 기기·등록 불명·ACK 유실·늦은 옛 ACK | SPIKE 지정 의도/확인 사례. 실제 세션 두 기기·새 의도 간 경쟁 검증 |
| RC-07 | 원거절 재전송·원승인 뒤 취소/종료·새 재개 | SPIKE 원판정 사례. 원내용·원판정·원 R 불변과 현재 상태 분리 검증 |
| RC-08 | 전역 outbox ID와 레인별 commit 역전·전송 유실 | SPIKE §4 역전 관찰. 회차/세대 tuple 재생·개인정보 분리 검증 |
| RC-09 | 복원으로 버전 감소·원키 이력 소실·옛 cursor | SPIKE §8 미검증. 세대 전환·불명 보류·중복 재실행 차단 검증 |
| RC-10 | 200연결 조회/입찰/worker pool 경쟁·재시도 폭주 | SPIKE §7 200연결 FAIL. 대기 분포·timeout·미결 적체와 보호 후보를 함께 측정 |
| RC-11 | 다른 lane의 같은 키 충돌·ACK/접수/제어 잠금 순환 | 새 잠금 그래프·고유 제약·rollback 재시도에서 순서/원기록 보존 검증 |
| RC-12 | 공개 직전 등록/수정/재배정·회차 시작/취소 동시 실행 | SPIKE 범위 밖. Round 순서·진행 점유·공통 시작·부분 실패 복구 별도 검증 |

100연결 지정 부하의 통과를 위 새 후보의 성능 보장으로 사용하지 않는다. 200연결 pool 실패와 미측정 항목은 SPIKE §7·§8을 유지한다.
관측 지표 후보는 접수/pool/gate 대기, 접수→판정 적체, 미결 최장 나이, 중복·충돌·ACK 지연, outbox 적체, commit 불명 수다.
로그에는 request/command 상관 식별과 scope만 남기고 비밀번호·토큰·세션·거래 이메일 등 민감값을 남기지 않는다.

## 11. 단계별 판단과 병렬 작업

D-095로 접수·공식 순서·원판정/ACK·동일 DB 원자성의 방향과 정의된 계약을 구현 기준선으로 채택했다. 접수 원시각/commit 경계, ADR-001/003 연계, 키·세대 수명, 권위 조회·잠금 순서·Round 보호 규약의 미해결 위험은 유지한다.
이번 채택은 RC 실행 PASS, 성능 보장 또는 배포 승인을 대신하지 않는다. 중요한 순서·원자성·복구 위험의 실제 보장은 운영 적용 전 실행 근거로 따로 판단하며 추가 실험 통과를 채택의 일괄 선행조건으로 두지 않는다.
병렬 가능: BE는 채택한 저장·명령 경계, FE는 같은 계약 버전의 등록/처리/원판정/ACK 흐름, QA는 RC·INV·TS 연결과 영향 경로 검증을 준비한다.
공유 테스트 fixture는 계약 0.1.0과 잔여 OPEN을 명시하고 승인되지 않은 수치·권한을 기대값으로 확정하지 않는다.
구현 에이전트는 계약 의미를 임의 변경하지 않는다. 변경안은 관련 D/INV·ADR·계약 diff와 소비자/QA 영향·증거를 제시하여 Contract Owner 검토와 사용자 승인을 거친다.
이 ADR은 접수/순서 기술 결정의 정본이다. API와 이벤트 payload 스키마의 정본은 `contracts/openapi.yaml`, 이벤트 순서·중복·재생 의미의 정본은 `contracts/auction-events.md`다. 동일 스키마를 여기 재기록하지 않는다.

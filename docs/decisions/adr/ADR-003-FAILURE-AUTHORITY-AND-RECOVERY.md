## 1. 문제와 공식 원본

장애를 뒤늦게 관측한 프로세스가 이미 시작한 판정이나 타이머를 계속 확정하면, 보류해야 할 상품을 낙찰·유찰할 수 있다.
프로세스 내부 flag, DB 재연결 성공, 운영자 확인 각각만으로 진행 권한이 복원됐다고 판단해서는 안 된다.
이 ADR은 승인된 장애 정책의 구현 후보를 비교하며, 새로운 장애 분류·종료·취소 권한을 만들지 않는다.

- 제품 정책 원본: [결정 기록](../DECISION-LOG.md)의 D-071~D-077, D-080; 시간은 D-067~D-070, 접수는 D-055~D-066.
- 도메인 책임 원본: [DOMAIN-MODEL](../../architecture/DOMAIN-MODEL.md) §6.6~6.7, INV-37~43, TV-04/10.
- 실행 증거 원본: [SPIKE-001](../../spikes/SPIKE-001.md) §6~8; [후속 결정 입력](../../spikes/SPIKE-001-DECISION-INPUTS.md).
- 이 ADR의 원본 범위는 진행 권한·장애 복구 설계다. API 경로·스키마·이벤트 필드는 후속 공통 계약 원본에서 정의한다.

## 2. 증거와 미검증 경계

| 관측 | 사용할 수 있는 근거 | 사용할 수 없는 보장 |
| --- | --- | --- |
| JVM 종료 40/40, SSE 경계 종료 20/20 | 지정 commit 경계에서 원기록·outbox 복구 | 두 앱 자동 판정 OFF와 명시적 `-Recover` 조건. 생존 peer 자동 진행 중 안전성 아님 |
| 실제 DB KILL/start 10/10 | postmaster epoch 변경 뒤 미완료 레인 보류 | 네트워크 분할·DB failover·임의 중단 시각 판별 아님 |
| worker 오류 처리 | 해당 JVM의 후속 pump 진입 차단, 별도 작업으로 보류 기록 | 이미 진입한 worker·다른 JVM·HTTP 접수의 원자적 차단 아님 |
| 중첩 중단 토큰 결함 수정 | 새 중단에 옛 재개가 적용되는 지정 반례의 회귀 | 동일 incident 반복 관측 병합·이력 불명 해제 절차 완성 아님 |

근거는 [보고서 §6](../../spikes/SPIKE-001.md#6-실제-장애와-재개-시각-관측)과 [입력 메모 §1](../../spikes/SPIKE-001-DECISION-INPUTS.md#1-현재-구현과-근거가-말하는-범위)이다.
실험의 500ms 보류 기록 주기는 감지·보류 완료 상한이 아니다. 장애 감지 시간·lease·재시도 임계값은 여기서 확정하지 않는다.
기존 `pg_xact_commit_timestamp` 계측은 PostgreSQL 커밋 기록 시각 기준이며 WAL flush·내구성 완료·락 해제 완료를 직접 측정한 값으로 사용하지 않는다.

## 3. 혼동하면 안 되는 식별자와 시각

다음은 의미를 구별하기 위한 후보 이름이며 최종 wire field·테이블 정의가 아니다.

| 이름 | 의미 / 수명 |
| --- | --- |
| `dbEpoch` | 현재 권위 DB 실행·복구 연속성의 관측 식별. spike의 postmaster 시작 시각은 재시작 탐지 근거이며 모든 복원·failover 세대를 대체하지 못함 |
| `authorityEpoch` | DB에 영속하는 진행 권한 세대. 프로세스 권한 교체 때 증가시키는 후보이며 소유자 식별과 함께 검증 |
| `processInstanceId` | 한 앱 실행의 식별. 호스트명·PID 재사용으로 동일성을 추정하지 않음 |
| `streamEpoch` | 회차·DB 복원 등에 따른 이벤트 버전 이력의 세대. 단순 앱 재시작·authority 교체와 반드시 같지 않음 |
| `incidentId` | 같은 실제 장애의 반복·복수 관측을 연결하는 식별. 모든 예외마다 새 장애로 만들지 않음 |
| `suspensionOccurrenceId` | 회차·레인의 해제 대상 중단 발생 건. incident, 수동 원인, epoch와 구별하며 옛 재개 차단에 사용 |
| `actualFailureAt` / 구간 | 실제 정상 접수·처리 연속성이 깨진 시점. 모르면 null 또는 증거로 제한한 구간으로 표현 |
| `observedAt` | 감지기가 장애 증거를 관측한 시점. 실제 장애 시각으로 소급하지 않음 |
| `holdCommittedAt` | 영속 보류가 확정된 경계. DB 불능 중에는 존재하지 않을 수 있음 |

`actualFailureAt ≤ observedAt ≤ holdCommittedAt` 같은 순서도 근거와 시계 조건을 확인해야 한다. 임의의 시계 차이로 선후를 증명하지 않는다.
원명령의 실제 재개 시각 `R`은 ADR-001의 전이 확정 경계를 따른다. 감지·확인·응답·이벤트 도착 시각으로 바꾸지 않는다.

## 4. 대안과 초기 채택

| 대안 | 해결하는 문제 / 비용 | 판단 |
| --- | --- | --- |
| JVM 내부 flag·메모리 락만 사용 | 구현이 작지만 중복 시작·재시작·진행 중 tx를 보호하지 못함 | 권위 경계로 채택하지 않음 |
| 단일 앱 + 영속 진행 권한 + 명시적 복구 | 노드 간 생존 판별·자동 takeover 범위를 줄이고 중복 시작을 차단 | **초기 구현 기준 채택, 위험 유지** |
| active/standby 자동 takeover | 가용성 개선 가능성, lease·fencing·분할·old tx와 복구 선후 입증 필요 | 초기 MVP 미지원, 별도 ADR·실험 필요 |
| 복수 active 판정 앱 | 여러 노드 실행 가능성, 같은 레인 순서 외에 장애 권한·부분 가용성 계약 필요 | 초기 MVP 미지원, spike의 두 JVM으로 승인되지 않음 |

초기 구조는 권위 PostgreSQL 1개와 앱 인스턴스 1개, 단일 활성 진행 주체로 제한하는 안을 채택했다. 배포 실행·운영 검증 승인은 별도다.
한 앱 안에서 1~4레인 worker는 독립 실행할 수 있다. 정상 경로를 전역 단일 판정 큐로 직렬화한다는 뜻이 아니다.
REST 접수·판정·타이머·회차 자동 전이는 같은 권한 규약을 사용하고, SSE 송신은 판정 트랜잭션 밖에서 수행한다.
운영 read replica·복수 active 앱·자동 DB failover는 이 초기 토폴로지의 지원 범위에 넣지 않는다. 가용성·무중단 배포 보장은 없다.
단일 앱 사망 때 정상 접수 연속성의 증거가 없다면 재기동은 복구 경계로 진입한다. 모든 JVM 사망을 무조건 전체 장애로 분류하는 제품 정책은 추가하지 않는다.

## 5. 진행 권한의 구체 후보와 중복 시작 차단

**후보:** DB의 영속 authority 기록과 전용 연결의 session advisory lock을 결합한다. 이 조합은 제품 구현·새 실험 모두 NOT_RUN이다.

1. 앱은 시작 시 외부 업무 변경을 차단한 상태에서 권한 획득을 시도한다. 중복 앱은 접수·worker·타이머를 활성화하지 않는다.
2. 단독 세션 락 획득만으로 재개하지 않는다. 직전 owner·DB 세대·clean 종료·미완료 작업·보류 기록을 검토한다.
3. 이전 실행의 연결·트랜잭션 결말을 확인한 뒤 authority 배타 경계에서 새 owner와 증가한 epoch, 복구 상태를 영속한다.
4. 정상 변경은 authority 검증과 레인 gate를 같은 트랜잭션 규약으로 사용한다. 일반 검증은 레인별 동시성을 유지할 수 있어야 한다.
5. 후보 검증 순서는 authority guard → 필요한 회차/레인 gate이며, 역순 획득·복구 락 upgrade는 피한다. 최종 락 순서는 ADR-002와 함께 검증한다.
6. 세션 락 연결의 단절·권한 불명은 후속 작업 진입을 차단한다. 단절한 전용 연결의 자동 재연결로 권한이 복원됐다고 간주하지 않는다.
7. 새 authority 전환은 DB 배타 경계 안에서 수행하고 정상 mutation과 경합시킨다. 오래된 epoch의 새 mutation은 저장 전에 실패해야 한다.

트랜잭션 전체에서 authority 행의 공유 guard를 유지하고 권한 전환이 배타 guard를 요구하는 방식은 비교할 fencing 후보다.
단순히 tx 시작 때 epoch를 읽거나 SQL `WHERE epoch = ?`를 한 번 검사하는 것만으로 commit 직전 권한을 보장했다고 주장하지 않는다.
session 락 연결과 worker 연결은 서로 다를 수 있다. 소유 연결이 끊겨도 다른 연결의 진행 중 tx가 즉시 취소되는 것은 아니다.

## 6. 이미 진행 중인 작업의 확정 권한

이 절은 미해결 기술 위험이며 D-095의 채택으로 해결·입증된 항목이 아니다. local flag를 확인한 시점부터 commit까지 새 장애가 발생할 수 있다.
이미 레인 락과 authority 공유 guard를 보유한 old worker가 있으면 새 owner의 배타 guard는 기다릴 수 있고, old tx는 먼저 commit할 수 있다.
따라서 epoch와 공유/배타 락의 조합만으로 실제 장애 이후의 모든 old commit을 차단했다고 주장할 수 없다.

- 초기 MVP에서는 timeout·lease 만료만으로 새 owner를 자동 활성화하지 않는다. old 프로세스·DB 세션 종료, rollback/commit 결말과 이력을 확인한다.
- 진행 중 tx의 종료·격리·재검증과 복구 배타 경계가 어떻게 경쟁하는지 FA-03/04/05에서 확인한다. 락 대기를 안전한 takeover 완료로 보고하지 않는다.
- 외부 접수·판정·자동 종료는 권한 상실과 unknown interval을 함께 검사해야 한다. 정상 마감 선행 증거가 없으면 결과 확정 자격이 없다.
- 완전한 원접수·선행 이력의 입찰 판정과 낙찰·유찰·다음 상품 진행의 허용 여부는 별개다. 원입찰 복원 성공만으로 자동 진행하지 않는다.
- 검증에서 보류가 선행해야 할 결과가 이미 확정되면 구현 실패다. 잘못된 결과를 재개방하거나 운영자가 수정하는 보정으로 통과시키지 않는다.

정상 마감 선행 증거·actual outage 불명 구간·진행 중 확정권한을 동시에 만족하는 구현 증거 전에는 이 후보를 운영 보장으로 채택하지 않는다.

## 7. 장애 관측, DB 불능과 보류 범위

| 사례 | 진행·보류 판단 |
| --- | --- |
| 특정 레인만 영향받았다는 증거가 충분 | 해당 레인만 보류, 다른 레인 권한·이력 연속성 검증 |
| 정상 접수 불능이 서비스 전체이거나 영향 범위 불명 | 현재 회차 미완료 레인 보류. 이미 확정된 결과·미래 모집 정책은 변경하지 않음 |
| 한 개인의 응답 유실·연결 단절·단순 조회 기록 없음 | 원키 확인과 회원×경매 미확인 제한 유지. 이것만으로 전체 경매 보류하지 않음 |
| SSE-only 송신 실패, 입찰 접수·판정·저장 정상 | 연결 종료·재동기화 경로. 전파 실패를 자동으로 업무 장애 보류에 결합하지 않음 |
| pool 포화 등으로 정상 접수·기록 가능성도 불명 | 전파 전용 실패와 구별하여 권한·영향 증거 검토. 단순 SSE 오류로 축소하지 않음 |
| DB 접속 불능 | 관측 후 local 차단은 보호 수단일 뿐 영속 보류가 아님. DB에 저장 불가능한 보류를 저장 성공으로 응답하지 않음 |

DB 복귀 시 최초 guarded mutation보다 먼저 복구 경계를 수행하고, 원마감이 지났다는 이유로 자동 종료하지 않는다.
마지막 확인 가능한 연속성 증거부터 복구 검증까지 unknown interval을 보존한다. 이 구간 전체가 실제 장애였다고 확정하지 않는다.
최초 장애 시각을 모르면 최초 관측 시각이나 재접속 시각을 임의 대입해 정상 마감 선행을 증명하지 않는다.
정상 마감 선행이 확인되면 정상 종료를 적용하고, 장애 선행·선후 불명이면 D-072대로 보류한다. 이미 확정된 결과는 유지한다.
현재 spike의 postmaster epoch guard는 재시작 반례 근거다. postmaster 값이 같은 네트워크 단절도 별도 연속성 검증 대상이다.

## 8. 복구 증거, 확인과 재개

복귀·권한 재획득·데이터 확인·운영자 확인·실제 재개는 서로 다른 단계다. 앱 기동은 경매 재개가 아니다.

1. 외부 새 변경·자동 진행을 차단하고 incident와 영향 후보 범위, DB/authority 세대, 미확정 tx 결말을 수집한다.
2. 원접수·공식 순번·원최종 판정·입찰 효과·최고가/최고입찰자·단계·시간 경계·결과 존재·미결 요청을 대조한다.
3. 원최종 판정은 재사용한다. 선행 이력이 완전한 미결 요청만 원시각·원순번으로 판정하며 현재 상태로 원거절을 재심사하지 않는다.
4. 결과·효과 존재 불명은 `historyComplete=false` 보류를 유지한다. 추정 거절·유찰·취소·미접수 종료로 대체하지 않는다.
5. 정상 접수·기록 가능성과 영향 범위의 증거를 확인하고, 현재 suspension occurrence에 결합한 운영자 복구 확인을 기록한다.
6. 확인만으로 수동 중단 원인이나 장애 보류를 제거하거나 시간을 새로 부여하지 않는다. 재개 가능 상태를 준비할 뿐이다.
7. 운영자가 현재 발생 건을 지정한 명시적 재개를 요청하면 공통 순서에서 원인·확인 증거·정상 접수/기록 조건을 다시 검증한다.
8. 유효 재개만 ADR-001의 원 R부터 보존 단계의 회차 고정 시간 전체를 부여한다. 부분 확인·새 장애 발생 때 기존 확인은 재사용하지 않는다.

`historyComplete=false`의 복원 관리는 별도 관리 작업 후보로 제안한다: 권한 있는 운영자가 증거 참조·복원 범위·판단 근거를 제출하고 재검증 결과를 영속한다.
이는 상태를 true로 덮어쓰는 버튼이 아니다. 이력·효과·결과 검증 실패면 계속 보류하며, 성공해도 복구 확인과 명시적 재개를 따로 요구한다.
관리 API·세부 접근 권한·증거 승인 책임·감사 보존은 후속 계약에서 승인받는다. 기존 spike에는 이 해제 절차가 없다.

## 9. incident·중단 발생 건·원명령

- 같은 incident의 반복·복수 관측은 증거를 추가하고 동일 원인을 병합한다. 관측 횟수만으로 새 발생 건을 무한 생성하지 않는다.
- 새로운 수동 중단·새 장애 원인·영향 범위 확대는 현재 해제 대상과 확인 유효성을 재검증하고 새 발생 건을 만드는 후보로 다룬다.
- 동일/새 incident 판별 기준이 불명하면 기존 확인으로 재개하지 않는다. 병합·분리 기준은 FA-10 검증·후속 상세화 대상이며 정의된 계약 의미를 바꾸려면 변경 절차를 따른다.
- 수동 원인과 장애 원인을 독립 보존한다. 장애 확인은 수동 중단을 해제하지 않고 허용된 명시적 재개에서 대상 원인을 검증한다.
- 운영자+명령 번호에 종류·회차/레인·발생 건·사유를 결합한다. 원판정·원 R·원내용을 보존하고 충돌은 원명령 변경으로 처리하지 않는다.
- 성공한 옛 재개의 재전송은 원결과·원 R만 반환한다. 현재 새 중단은 유지하고 새 시간·이벤트 효과를 생성하지 않는다.
- 한 번도 접수되지 않은 옛 발생 건 재개도 현재 새 발생 건을 해제하지 못한다. 진행 중 새 키 재개 역시 시간을 갱신하지 않는다.
- 보류 취소는 D-075의 결과 없음·선행 요청/상태 확인·사유 조건을 적용한다. 확인 불능을 취소로 우회하지 않는다.

## 10. 공통 계약과 관측에 미치는 영향

채택한 계약은 접수 전 가용성 실패, 공식 접수 후 처리 확인 중, 원최종 업무 판정, 권한 불명·복구 보류를 구분한다.
HTTP 오류·timeout·SSE 수신만으로 원요청 거절·미확인 해제를 표현하지 않는다. 재시도는 ADR-002의 같은 키·고정 내용 경로를 따른다.
운영 조회에는 원인·발생 건·확인 유효성·보류 범위·증거 상태를 제공하는 안을 검토하되 내부 식별·개인정보 공개 권한을 자동 확대하지 않는다.
공개 상태·이벤트는 보류와 실제 재개를 구별하고, 세대 변경·재생 불가 시 snapshot 동기화한다. 보류 이벤트 송신은 보류 commit을 대체하지 않는다.
정의된 wire 오류 코드·경로·필수 필드·버전은 공통 계약 0.1.0이 원본이다. 남은 OPEN을 임의로 채우거나 이 ADR을 구현 에이전트의 독자 변경 근거로 사용하지 않는다.

로그·지표는 authority owner/epoch 변경, guard 거절, incident 관측·병합, 보류 commit, 미결 최장 지연, 복구 확인·재개를 연결한다.
actual/observed/hold 시각과 unknown 구간·시계 전제를 구분하고 pool 대기·worker 진행 중 tx·SSE-only 오류를 원인별로 관측한다.
명령/요청/회차/레인/발생 건의 상관 식별을 사용하되 비밀번호·토큰·세션·입찰자 개인정보를 로그로 출력하지 않는다.
알림·timeout·lease 임계값, 장애 감지·복구 시간 SLO는 실험·운영 근거 없이 숫자로 확정하지 않는다.

## 12. 채택 범위와 남은 제약

D-095로 단일 앱·단일 활성 진행 주체, 영속 진행 권한의 경계와 명시적 복구를 초기 구현 기준으로 채택했다. 자동 takeover·다중 active·장애 감지 상한은 채택 범위가 아니다.
authority guard·session 락·epoch의 정확한 결합, old tx 확정권한, incident 병합과 이력 복원관리는 미검증 후보·위험으로 유지한다. 구체 후보의 모든 세부가 이미 완성됐거나 검증됐다는 승인이 아니다.
설계·계약 채택과 구현의 FA 실행 PASS·운영 보장 주장은 서로 다른 판단이다. 추가 실험을 이번 채택의 일괄 선행조건으로 두지 않으며, old tx 확정권한과 복구 선후 위험은 운영 적용 전에 따로 해결·검증해야 한다.
구현·변경 시 ADR-001의 전이 시각과 ADR-002의 접수/락 순서를 대조하고, 채택한 역할별 API·오류·복구 상태의 원본 연결을 유지한다.
FA-01~14 중 해당 구현 경로의 실패·미실행이 남으면 운영 정합성·failover·감지 상한을 보장했다고 기록하지 않는다.
초기 한계는 앱 정지 시 가용성 상실, 명시적 복구 대기, 권위 이력 불명에 따른 장기 보류·후속 회차 대기다. 자동 강제 종료는 제안하지 않는다.
**현재 결론: D-095의 범위로 ACCEPTED_WITH_OPEN이다. 구체 guard·old tx 안전성은 미입증이며 제품 구현·새 장애 시험·배포 검증은 모두 NOT_RUN이다.**

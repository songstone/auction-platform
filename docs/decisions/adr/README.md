# 아키텍처 결정과 승인 범위

작성일·채택일: 2026-10-15. 초기 작성 지시 뒤 추가 실험을 선행하지 않고 시스템 설계·계약을 검토했다. 이후 사용자가 남은 OPEN과 미검증 위험을 유지한 현재 시스템 설계·정의된 API·이벤트를 구현 기준선으로 명시 승인했다(D-095). **ADR-001~005는 ACCEPTED_WITH_OPEN이며 구현·실행 PASS·운영 보장을 뜻하지 않는다.**

채택 기준선은 SYSTEM-DESIGN 1.0(출발 검토본 0.2), 공통 계약 0.1.0(출발 검토본 0.1.0-draft.2)이다. 승인 이력·범위는 [DECISION-LOG](../DECISION-LOG.md), 대상 파일·hash 식별은 [계약 기준선 안내](../../../contracts/README.md)가 연결하는 기록이 원본이다.

2026-10-16 추가 채택: D-096·ADR-006이 JPA 엔티티·도메인 통합과 Spring Data Repository 사용을 확정했다. SYSTEM-DESIGN 1.1 / DOMAIN-MODEL 1.3이며 공통 계약은 0.1.0을 유지한다. 이전 D-095 기준선은 이력으로 보존하고 현재 파일 식별은 계약 안내의 새 아키텍처 기준선을 따른다.

## 채택 상태와 적용 범위

- ADR·시스템 설계·정의된 공통 계약을 D-095의 범위로 구현 기준선으로 채택했다. 신규 서비스 구현·실험·부하·장애 시험은 **NOT_RUN**이다.
- 기존 spike의 성공·실패·원자료는 새 시험 결과로 합산하지 않는다. 시간 계측의 커밋 기록 시각과 물리 내구성 완료 시각의 차이를 보고서에 명확히 한다.
- ADR-001의 B 구체화 방향은 채택했지만 정확한 활성화 메커니즘·실제 S/N/R·전체 시간 충족은 미해결이다. ADR-002/003의 채택도 실제 SQL·guard·old tx 안전성의 입증이나 운영 보장이 아니다.
- 기술 검증의 책임은 설계·구현·QA 담당에게 있다. 이미 승인된 업무 정책을 다시 OPEN으로 돌리거나 반례의 기대값을 사용자에게 정하게 하지 않는다.
- 구조는 ADR-004의 스택·조건부 C·참여 상태 분리·공개 확정 시 Auction 생성을 채택했다. 조회 자원 보호의 세부·인증/권한·입력 범위·실시간 세대/재생의 남은 OPEN과 미검증은 계속 구분한다.

## 후속 산출물과 병렬화

추가 실험 통과를 진입 조건으로 두지 않고 작성한 [SYSTEM-DESIGN](../../architecture/SYSTEM-DESIGN.md)과 [공통 계약](../../../contracts/README.md)을 D-095로 채택했다. 미검증 메커니즘은 가정·미해결 위험·NOT_RUN을 유지한다. 정확한 경로·스키마·전파 의미는 채택 계약 0.1.0의 원본을 따른다.

설계·계약 채택, 구현의 실행 검증, 실제 운영 적용을 별도로 판단한다. 이번 채택은 가정과 NOT_RUN을 유지한 구현 기준선 승인이다. 실행 PASS나 시간·정합성·성능 보장을 대신하지 않으며 중요한 미해결 위험은 운영 적용 전에 따로 해결·검증한다.

| 담당 | 지금 가능한 작업 | 채택·검증·운영의 별도 조건 |
| --- | --- | --- |
| 백엔드 | 채택한 모듈·포트·트랜잭션·API와 승인 불변식에 따른 설계·구현 준비 | 기준선의 남은 OPEN을 식별. 권위 전이·장애 처리의 실제 보장은 실행 근거 필요 |
| 프런트엔드 | 계약 0.1.0 소비자·mock, 등록/접수/최종 판정/앱 확인 상태 구분 | 같은 승인 버전으로 맞추며 실제 연동·복구 통과는 별도 확인 |
| QA | AC·INV·TS에서 독립 기대값 도출, TM/RC/FA 검증 계획 검토 | 남은 OPEN을 임의 합격 기준으로 사용하거나 새 실행 없는 PASS 기록 금지 |

독립 구현의 공통 기준은 D-095의 승인 범위와 계약 0.1.0의 경로·스키마·오류·이벤트·재동기화 의미, 검토한 예제·인증/권한 표다. 남은 정책 값·deferred·미검증 작업까지 모두 완료됐다고 판단하지 않는다.

## 변경·검토·승인 절차

1. 구현 담당은 계약을 임의로 수정하지 않고 관련 R/D/INV·ADR, 변경 이유, 예시, 호환성·BE/FE/QA 영향을 담은 변경안을 제출한다.
2. Contract Owner가 각 사실의 원본을 수정하고 관련 문서는 참조로 맞춘다. 구현 코드에만 새 오류·필드·상태 의미를 추가하지 않는다.
3. BE/FE/QA가 서로의 구현과 독립적으로 변경 예제·권한·경계·복구 의미를 검토한다. 정적 검사와 실행 증거를 구분한다.
4. D-095는 현재 정의된 범위의 명시적 채택 승인으로 기록한다. 이후 변경도 해당 선택의 채택을 사용자가 명시적으로 승인한 뒤 범위·가정·검증 상태·계약 버전을 갱신한다. 작성 지시·실험 방향·실행 승인은 계약 변경 승인이 아니며 검증하지 않은 운영 보장을 포함하지 않는다.
5. 공통 계약 확정 시 파일 목록·버전·Git commit 또는 hash로 기준선을 식별한다. 이후 변경도 같은 절차를 따르며 파괴적 변경은 이행 방식을 포함한다.
6. CODEOWNERS·보호 브랜치·계약 lint·예제 검증·호환성 diff를 CI 후보로 둔다. 현재 설정되어 있거나 무단 변경을 이미 차단한다고 주장하지 않는다.

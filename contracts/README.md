# 공통 계약 기준선 안내

| 항목 | 값 |
| --- | --- |
| 계약 버전 | **0.1.0** |
| 상태 | **USER_APPROVED — 정의된 API·이벤트의 구현 기준선, 남은 OPEN·미검증 위험 유지** |
| 승인 근거 | D-095. SYSTEM-DESIGN 1.0과 현재 정의된 계약 범위 채택 |
| 작성일 | 2026-10-15 |
| 담당 | Solution Architect & Contract Owner. 최종 승인자는 사용자 |
| 새 실행 | 제품 구현·기능·DB·동시성·장애·브라우저·성능·배포 검증 **NOT_RUN** |

사용자가 남은 OPEN과 미검증 위험을 유지한 채 현재 시스템 설계와 정의된 API·이벤트를 구현 기준선으로 승인했다(D-095). 기존 `0.1.0-draft.2`의 wire 정의를 바꾸지 않고 계약 버전을 `0.1.0`으로 식별한다. 설계·계약 채택 승인, 정적 검사, 실제 구현 검증, 운영 적용은 따로 판단한다. 미정 입력 제한·보안 수명·deferred 표면까지 모두 완성됐다는 승인은 아니다.

[CONTRACT REVIEW 001](../docs/decisions/CONTRACT-REVIEW-001.md)은 제품 결정·기술 채택·구현 검증의 승인 범위를 기록한다. CR-01~03은 **D-092 운영자/회원 계정 분리, D-093 최저낙찰가 단위 정렬 미요구, D-094 유찰 최고입찰가 미노출**로 승인됐다. D-095는 기존 시스템·계약 원칙과 정의된 부분을 채택하며, **CR-04~10·SEC-01~04와 남은 OPEN의 제안값은 승인하지 않는다.** 현재 승인 기준선의 파일별 hash는 [approved-baseline-0.1.0.json](approved-baseline-0.1.0.json)이 원본이다. [review-baseline.json](review-baseline.json)은 승인 전 검토 이력이며 현재 승인 파일 식별로 사용하지 않는다. 승인 상태·버전·manifest 동기화의 새 정적 검사와 독립 문서 검토를 통과했다.

## 2. 이번 wire 선택의 의미

다음은 **D-095로 채택한 정의된 wire 표현의 요약**이며 정확한 자료형·pattern·필수 조건은 OpenAPI가 원본이다. 승인 범위에 포함되지 않은 OPEN·보안/운영 수치와 실제 구현의 보장은 별도로 남긴다.

| 선택 | 이유·해석 |
| --- | --- |
| OpenAPI 3.1.1 + JSON Schema 2020-12 계열 Schema Object | HTTP와 이벤트 JSON을 하나의 기계 판독 원본으로 관리. 문서 버전과 계약의 `info.version`은 별개 |
| 리소스 ID·요청/명령/결과 식별·cursor는 opaque 문자열 | 동일성으로만 비교. UUID·숫자 순서·문자열 정렬·대소문자 변환을 임의 가정하지 않음. `laneId`는 별도로 회차 안의 1~4 레인 번호 |
| KRW 금액은 양의 정수 십진 문자열 | JavaScript 정수 표현 한계와 DB 숫자형 한계를 제품 금액 상한으로 바꾸지 않음. 앞의 0·부호·소수·지수 표현 없이 전달 |
| 상태 version은 0 이상, 공식 접수 순번은 양의 정수 십진 문자열 | 정밀도 손실 없는 비교. 숫자값 비교는 같은 scope·세대에서만 허용하며 ID와 혼용하지 않음 |
| 시각은 UTC `Z`의 RFC 3339 프로파일 | 원기록의 소수 정밀도를 보존하고 선택적 소수부는 최대 6자리. 실제 시계 정확도·물리 해상도·접수 정밀도 달성의 승인이 아님 |
| `serverTime`은 서버 시계 표본 | 응답 수신 시각·공식 입찰 접수·전이 확정 시각을 대신하지 않음. 일정 해석·표시는 Asia/Seoul |
| 동일 출처 보안 쿠키 + CSRF 헤더 | `AUCTION_SESSION`의 Secure·HttpOnly·SameSite=Lax와 `GET /api/v1/auth/csrf`에서 받은 `X-CSRF-Token` 사용. 세부 수명·재설정 정책은 OPEN-06 |
| 공개 레인 상태와 개인 원판정 분리 | 공개 SSE와 snapshot은 같은 공개 상태 스키마 사용. 본인 원요청·원판정·ACK는 인증된 REST로 복구 |

금액 pattern은 `^[1-9][0-9]*$`, version pattern은 `^(0|[1-9][0-9]*)$`, 공식 접수 순번은 양의 정수 pattern을 사용한다. 이는 wire 정규화이며 미정 금액·시간 상한을 승인한 것이 아니다. 클라이언트는 금액·version을 손실 가능한 JSON number로 변환하지 않는다.

RFC 3339 자체가 UTC `Z`나 소수부 6자리를 강제하는 것은 아니다. 이 제한은 본 계약의 표현 프로파일이다. 시각 절삭·반올림으로 경계 판정을 달리하거나 화면 시각으로 원접수를 재작성하지 않는다. 실제 S/N/R 취득과 내구성·시계 연속성은 [ADR-001](../docs/decisions/adr/ADR-001-TRANSITION-TIME.md)의 구현 위험으로 남긴다.

## 3. 접수·판정·확인 경계

- 공유 의도의 등록·등록 확인은 실제 입찰 접수가 아니다. 등록돼도 아직 제출되지 않았을 수 있으며 등록 시각으로 마감을 판정하지 않는다.
- 실제 제출의 `202`는 **공식 접수가 내구 확정됐고 아직 원판정이 없는 경우**에만 사용한다. 공식 접수 성공과 입찰 승인을 같은 이름으로 표시하지 않는다.
- 이미 최종 판정이 있는 동일 내용 재전송은 `200`으로 원판정을 반환한다. 업무상 거절은 불변 결과 본문의 `REJECTED`이며 프로토콜 충돌 `409`로 대체하지 않는다.
- 내용 충돌·이미 다른 미확인 의도 존재에 대한 `409`는 원입찰 최종 거절이 아니다. `404` 원요청 조회 없음, 인증 실패, 시간초과·`5xx`로 원요청의 미확인 제한을 해제하지 않는다.
- 활성 공유 의도 조회의 `200` + `null`은 그 조회에서 활성 의도가 없다는 뜻이다. 지정한 잘못된 원키의 `404`와 구별하며, 단순 부재를 기록 소실·효과 불명의 안전한 종료로 사용하지 않는다.
- 앱은 원최종 판정을 수신·반영한 뒤 원요청에 결합한 `outcomeId`로 자동 ACK한다. 어느 기기의 일치 ACK든 해당 의도만 해제하며 옛 ACK가 새 의도를 해제하지 않는다.
- 응답 유실·세션 만료 뒤에는 재인증하고 같은 키·내용으로 조회·재전송한다. SSE·snapshot 수신은 개인 원판정 ACK가 아니다.

이 구분의 경로·응답·오류 코드·ACK 필드는 OpenAPI에서만 정의한다. 원접수·원순번·원판정과 불명 복구의 기술 원본은 [ADR-002](../docs/decisions/adr/ADR-002-DURABLE-RECEIPT-AND-ORDERING.md), [ADR-003](../docs/decisions/adr/ADR-003-FAILURE-AUTHORITY-AND-RECOVERY.md)이다.

## 4. 범위와 미결정 경로

OpenAPI의 `x-open-decisions`, `x-draft-status`, `x-verification-status`, `x-deferred-surfaces`는 각각 남은 결정 연결, 정의 완성도, 실행 증거, 아직 모델링하지 않은 표면을 표시하는 **문서용 확장**이다. 서버가 이를 자동 집행한다고 가정하지 않는다. `x-draft-status`의 이름과 분류는 전체 계약의 USER_APPROVED 상태와 다른 축이다. `draft-with-open-policy` operation도 정의된 부분은 기준선에 포함하지만, 남긴 정책 빈칸을 구현자가 임의 채워 동작·합격 기준을 확정하지 않는다. 다른 승인 범위의 구현은 병렬로 진행할 수 있다.

| 기능 묶음 | 요구사항 연결 | 구현 기준선의 정의 범위·남은 경계 |
| --- | --- | --- |
| 공개 회차·상품·레인·결과 조회와 SSE | R-02, R-04, R-27~R-34, R-37, R-38, R-42, R-44 | 공개 상태·snapshot·재생 의미를 모델링. 유찰 최고입찰가 미노출은 D-094로 승인됐으며 낙찰자 식별 상세는 미정 |
| 공유 의도·실제 입찰·원판정·ACK | R-08~R-26, R-49 | 등록/접수/최종 판정/확인을 구분. 원키·금액·원경매 유지와 미확인 복구를 공통 사례로 사용 |
| 출품·사진·공개 고정·재출품 | R-07, R-28, R-32~R-36, R-40, R-46 | 알려진 필수값·양의 정수·소유권은 표현. 미정 입력 제한을 쓰는 경로의 구현 제한은 operation별 표시 |
| 회차 설정·일정·레인 제어·상품 취소·복구 | R-07, R-15, R-24~R-31, R-41~R-44, R-46, R-52 | 원명령·원대상·발생 건·원 R·순서 보존. 시간/일정 범위·복구 증거의 미정 세부는 분리 |
| 가입·검증·로그인·비밀번호 재설정 | R-16, R-17, R-45, R-47, R-50, R-52 | D-092에 따라 운영자는 운영 전용 계정, 회원 기능은 별도 일반회원 계정. 미정 계정·세션/CSRF·보안 조건은 operation별 표시 |
| 본인 기록·당사자 연락처·제한 조회 | R-38, R-39, R-51 | 본인/낙찰 당사자 범위. 운영자 포괄 조회 권한·미정 식별 필드는 제공하지 않음 |
| 정합성·응답·전파·재접속 인수 | R-48, R-49 | 계약 예제·기대 상태를 제공. 실제 부하 구성·측정·보장 성공은 별도 검증 |

위 표는 탐색용 기능 지도이며 모든 R을 단일 operation으로 완전 구현했다는 체크리스트가 아니다. 필수·허용값의 정확한 범위는 OpenAPI의 각 operation과 연결된 승인 기준을 확인한다.

| 남은 결정 | 계약에서의 처리 |
| --- | --- |
| OPEN-01/02 | 일정 입력 정밀도·미래 범위·지연 안내의 세부를 미정으로 표시. 이미 승인된 모집/공개/시작 순서는 유지 |
| OPEN-05 | 최저낙찰가의 단위 정렬 미요구는 D-093으로 해결. 잔여 금액/시간 범위·단위 후보·문자 길이·사진 제한을 임의 채우지 않음. 해당 operation·스키마의 `x-open-decisions`를 확인 |
| OPEN-06 | 운영자/회원 계정 분리는 D-092로 해결. 계정 판정 상세·세션/재설정 수명·기타 보안 조건은 미정 |
| OPEN-07 | 유찰 최고입찰가 미노출은 D-094로 해결. 낙찰자 식별 필드·전체 입찰 이력·추가 운영자 조회는 deferred. 공개 낙찰가와 비공개 최저낙찰가 구분 유지 |
| OPEN-08 | 브라우저·모바일 배치·자동 전환 결과 표시 방식/시간 미정. 공개 상태 복원 의미와 구별 |
| OPEN-09/10 | 전이·공식 기록·권한·복구·재시도 세부를 ADR과 연결. D-095의 설계·계약 채택은 미완성 메커니즘의 정확성 입증이 아님 |
| OPEN-12/14 | 운영 보존·개인정보·실거래 운영의 후속 결정. 진행/보류/미확인 원기록의 MVP 자동 만료 없음은 유지 |
| OPEN-13 | 인수 환경·표본·실패 처리·측정 경계 미정. 문서 검사와 성능 PASS를 합치지 않음 |

`NO_SALE` 종료 응답·결과 화면의 최고입찰가 미노출은 D-094의 승인 정책이다. 진행 중 이미 본 가격이나 브라우저 기록의 삭제·회수를 뜻하지 않는다. 낙찰자 식별 상세 등 남은 정보 공개 범위는 임의 추가하지 않는다. D-093에 따라 양의 정수이며 시작가 이상인 최저낙찰가에 입찰 단위 정렬을 추가 요구하지 않는다. 상세 스키마와 deferred 표면은 OpenAPI가 원본이다.

## 5. 병렬 작업과 승인 기준선

| 담당 | 현재 가능한 작업 | 독립 구현의 공통 접점 |
| --- | --- | --- |
| BE | 승인된 정의의 command/query·원키·ACK·상태 흐름과 트랜잭션을 구현·검증할 준비 | 계약 0.1.0과 operation의 남은 OPEN·예제·권한/오류 의미 |
| FE | 승인된 응답/이벤트 예제로 등록 확인·공식 접수·원판정·ACK·재동기화 구성과 연동 준비 | 같은 상태 모델과 원키/금액 불변성, 공개/개인 상태 분리 |
| QA | 승인 AC/INV/TS와 계약 0.1.0에서 경계·충돌·권한·응답 유실·재생 기대값을 독립 도출 | 같은 예제·미결정 항목, 정적 검사와 실제 실행 증거의 구분 |

정의된 부분은 D-095와 승인 manifest에 식별된 계약 0.1.0을 공통 구현 기준선으로 사용한다. 입력 제한·세션 수명·deferred 응답 등 OPEN에 걸린 동작은 추가 결정 없이 채워 넣지 않는다. 승인 범위와 위험을 유지하므로 전체 프로덕션 준비 완료를 선언하지 않는다. 실제 서비스·장애·성능 통과는 별도 증거로 보고하며, 이번 승인 기록을 제품 코드 작성·서비스 실행 완료로 바꾸지 않는다.

변경 제안·호환성·버전·승인 절차는 ADR-005가 원본이다. 구현 에이전트는 공유 원본이나 자기 코드에서만 의미를 바꾸지 않고 Contract Owner에게 관련 R/D/INV·diff·소비자/QA 영향을 제출한다.

## 6. 검증 기록

| 검사 | 현재 상태 |
| --- | --- |
| 이전 계약 `0.1.0-draft.1` 정적 검사 이력 | **CONTRACT_STATIC_ONLY / PASS**. 당시 검사 수치는 아래 이력 문단에 보존. draft.2의 통과로 재사용하지 않음 |

이전 `0.1.0-draft.1`의 수동 정적 검사 이력은 41개 경로·45개 operation·91개 스키마의 명세, 내부 참조 714개, 공유 예제 21개, 실제 요청/응답에 연결한 예제 13곳, 음성 스키마 사례 35개, 변경 요청의 CSRF/403 선언 22개와 공개 스키마 4개 그래프의 지정 비공개 필드 부재다. 당시 이벤트 4종의 공통 union과 예제의 금액·시간 산술도 확인했다. 이 수치는 D-092~D-094를 반영할 draft.2의 실행 결과가 아니다. 권한 선언·필드 그래프 검사가 실제 권한 집행·정보 유출 방지 성공을 뜻하지 않는다. 음성 스키마 사례 35개는 ADR의 TM/RC/FA 실행 후보 35개와 별개다.

이전 `0.1.0-draft.2`에서는 공유 예제 24개·요청/응답에 연결한 예제 15곳·음성 스키마 사례 38개를 검사했다. 당시 D-092의 겸용 역할 세션 거절, D-093의 비정렬 최저낙찰가 출품/수정 예제와 산술, D-094의 유찰 종료 조회/이벤트 최고가 필드 거절을 확인했다. 이는 스키마와 합성 예제 검사이며 실제 권한 집행·입찰 처리·기록 보존의 성공 증거는 아니다. 현재 0.1.0에서도 같은 예제·검사를 새로 실행해 PASS를 확인했다. 승인 전 원본과 구조 대조 결과 경로·스키마·보안 선언·OPEN/deferred는 동일하고 승인 메타데이터만 변경됐다. 비교 범위·출발 hash·현재 파일 식별은 승인 manifest에 기록한다.

재실행은 저장소 루트에서 별도 Python 가상환경을 사용한다. 다음 명령은 계약 검증 도구만 설치하며 제품 서버를 실행하지 않는다.

```powershell
$contractVenv = Join-Path $env:TEMP 'auction-contracts-venv'
python -m venv $contractVenv
& "$contractVenv/Scripts/python.exe" -m pip install -r contracts/requirements-validation.txt
& "$contractVenv/Scripts/python.exe" contracts/validate_contracts.py
```

Python의 assert 검사를 끄는 `-O`/`PYTHONOPTIMIZE`를 사용하지 않는다. 성공하면 `validation-report.json`을 현재 OpenAPI hash와 도구 버전으로 갱신한다. 패키지 버전은 [requirements-validation.txt](requirements-validation.txt)가 원본이며 제품 의존성이 아니다.

CI 연동·계약 호환성 diff·CODEOWNERS/보호 브랜치는 후속 도입 후보이며 이미 강제되고 있다고 주장하지 않는다. 구조 검사 PASS를 런타임·보안·업무 정합성·운영 검증으로 확대하지 않는다.

## 7. 사용한 공식 규격

- [OpenAPI 3.1.1](https://spec.openapis.org/oas/v3.1.1.html#schema-object): Schema Object와 JSON Schema 방언의 연결을 정의한다. 본 계약의 명세 버전이며 최신 버전이라는 주장은 하지 않는다.
- [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core): 스키마 평가의 기준이다. 실제 validator의 지원·format 검사를 따로 확인한다.
- [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3): `202`는 처리가 완료되지 않은 상태다. 내구 접수 의미는 이 서비스가 추가로 정의한 계약이다.
- [RFC 3339 §5.6](https://www.rfc-editor.org/rfc/rfc3339.html#section-5.6): 타임스탬프 문법의 근거다. UTC·소수부 제한은 이번 wire 프로파일이다.
- [WHATWG SSE](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-last-event-id-header): `Last-Event-ID`는 재연결 식별 전달을 지원한다. 업무 replay·중복 제거·snapshot 인계는 이벤트 계약이 정의한다.
